### 3.3 🔴 P0 — MCP 会话只能服务一次，断开后彻底卡死

**现象**：第一次 MCP 连接完全正常（14 工具可用）；客户端断开后，**后续任何新连接全部失败**，返回：

```
{"code":-32600,"message":"Invalid Request: Server already initialized"}
```

已用 `test/mcp-reconnect.ts` 连续三次连接验证：A/B/C 全部失败，且服务器进程不崩溃、端口仍监听，但拒绝一切新会话。

**根因**：`packages/mcp/src/index.ts` 第 220 行在启动时只创建**一个** `StreamableHTTPServerTransport` 并复用它处理所有请求：

```ts
const transport = new StreamableHTTPServerTransport({ sessionIdGenerator: () => randomUUID() })
void server.connect(transport)
```

`sessionIdGenerator` 使 transport 进入「有状态」模式，该实例**只维护一个会话**。首个客户端 `initialize` 后 transport 被标记为已初始化；客户端断开（即使正常 close）后 transport 不重置，于是第二个客户端的 `initialize` 被拒「already initialized」。

**影响**：MCP 是产品核心卖点「AI 调试的手脚」。此 bug 意味着**同一进程生命周期内只能有一个 agent 连接一次**，之后所有 agent（DSH 等）都无法再接入，必须重启程序。正常 agent 工作流正是「连接→干活→断开」，等于每次使用后就要重启。

**建议修复方向**：按 MCP SDK 官方 streamable-http 模式，为**每个会话**新建一个 `StreamableHTTPServerTransport`（以 sessionId 为 key 缓存，会话结束时销毁），而非全局单例；或改用 stateless 模式并在每个请求前新建 transport。

> ⚠️ 提醒：本次测试已触发该 bug，**8081 MCP 现已处于卡死状态**，需重启程序才能恢复。
