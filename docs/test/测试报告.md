## 四、问题清单（按严重程度排序）

### 🔴 P0 — 历史数据多分组时间戳错位，另一组永远显示「—」（数据正确性）

**现象**：设备「测试从站」有 2 个分组，历史页查询后，**每一行的 20 列里永远有 10 列显示 `—`（数据不足）**，两组值无法在同一行对齐查看。

**根因（已用 API 实证）**：poller 每个分组独立轮询，两组的时间戳相差几十毫秒、**永远不重合**（实测同一时间戳最多只含 10 个地址，见 `test/repro-history-alignment.js`）。前端历史页却按「精确毫秒时间戳字符串」分组：

- `apps/web/src/App.tsx` 第 717–718 行：

```ts
const rawByTs = new Map<string, Record<number, number>>()
for (const p of pts) { if (!rawByTs.has(p.ts)) rawByTs.set(p.ts, {}); rawByTs.get(p.ts)![p.address] = p.rawValue }
```

结果每组时间戳各成一个 bucket，每个 bucket 只含一个分组的 10 个地址，另一组被判定为「数据不足」。

**证据**：`/api/data/object?object_id=1` 返回 20 个地址（0–9 与 4096–4105）各 ~2995 条数据、`/api/monitor_objects/1/latest` 也有全部 20 个地址，但 UI 表格第二组全 `—`。

**建议修复方向**：
1. 历史页按**时间桶对齐**（如向下取整到 1s 或轮询周期），把同一周期内的多组数据合并到一行；
2. 或改为**按寄存器各自成序列**（同曲线页思路），不做「同一行跨组」假设；
3. 曲线页 `App.tsx` 第 823–829 行有同样的 `rawByTs` 按精确 ts 分组的写法，对 16 位单字寄存器暂不影响，但多字寄存器（32/64 位跨组）可能同样受影响，建议一并核对。

### 🟠 P1 — 删除设备/分组无任何确认（数据安全）

**现象**：点侧栏设备上的「×」或分组上的「删除」，**立即删除，无确认对话框**（实测 `dialog` 未触发）。设备可能挂着多组多寄存器，误点即丢失配置。

**位置**：
- 设备删除 `apps/web/src/App.tsx` 第 291–295 行（`deleteDevice`），触发按钮第 357 行（`.device-del`）。
- 分组删除 `apps/web/src/App.tsx` 第 440 行（`deleteGroup`）。

**建议**：删除前弹确认（`window.confirm` 或复用现有 modal 组件），文案带上设备/分组名，提示「将删除其下 N 个分组/寄存器」。

---

### 🟠 P1 — 「新建设备」入口隐蔽，可发现性差

**现象**：全站**没有可见文字的新建设备按钮**。唯一入口是工作区行右侧的裸「＋」（`apps/web/src/App.tsx` 第 164 行），只带 `title/aria-label="新建设备"`，无文字。空状态页（第 391–393 行）也只有提示文字、没有 CTA 按钮。

**建议**：
1. 空状态页加一个「＋ 新建设备」主按钮（直接 `setShowAdd(true)`）；
2. 侧栏设备区标题旁加可见的「＋ 新建设备」按钮；
3. 保留现有「＋」但加 tooltip 之外的可见文字/更大点击区。

---

### 🟠 P1 — 写寄存器：无输入校验、无错误反馈、无成功提示

**现象**：
- 值输入框无格式/范围校验，`Number(value)` 可能得 `NaN`（`App.tsx` 第 543 行）；值为空时静默 `return`，无提示。
- 写失败时 `api.post` 的异常**未捕获**（`api.post` 第 111 行无 `.catch`），会变成未处理 rejection，UI 无任何反馈。
- 写成功后弹窗直接关闭，无「已写入」反馈。

**位置**：`WriteModal` 第 532–566 行。

**建议**：写前校验（空值/NaN/越界提示）；`try/catch` 捕获失败并在弹窗内显示错误；成功给个短暂成功态（如 toast 或按钮文案「已写入」）。

---

### 🟡 P2 — 移动端无响应式布局（可用性）

**现象**：`apps/web/src/styles.css` **完全没有 `@media` 查询**。侧栏固定 `width:264px; min-width:264px`（第 59 行），在 375px 手机上主区只剩 111px，寄存器表（地址/别名/类型/值 4 列）被压进 111px 内横向滚动，几乎不可用。

**建议**：
1. 手机端侧栏折叠为抽屉/汉堡菜单，主区占满屏；
2. 寄存器表在窄屏改为卡片式或横向滚动容器 + 粘性首列；
3. `reg-modal` 固定 `width:360px`（第 112 行）无 `max-width`，<360px 视口会溢出，建议加 `max-width:92vw`（`settings-modal` 已这么做，可对齐）。

---

### 🟡 P2 — 缺 favicon，产生 404 + console.error

**现象**：`apps/web/index.html` 未声明任何 favicon，浏览器自动请求 `/favicon.ico` → 404，控制台出现 `Failed to load resource: 404`。

**建议**：在 `index.html` 加 `<link rel="icon" ...>`，或在 `@fastify/static` 层提供默认图标。

---

### 🟡 P2 — 静态资源未开启压缩

**现象**：JS bundle 182KB 以**未压缩**形式下发（`Content-Encoding` 为空），gzip 后约 45–50KB。本地影响小，若部署到内网/远程可优化。

**建议**：在 Fastify 加 `@fastify/compress`（gzip/brotli）。

---

### 🟡 P2 — API 层无统一错误处理，历史查询静默吞错

**现象**：
- `api.get/post/put/del`（`App.tsx` 第 109–114 行）直接 `.then(r => r.json())`，后端报错时产生未处理 rejection，UI 无任何反馈（设备列表静默为空等）。
- 历史查询 `query` 的 `catch { setStatus('done') }`（第 729 行）会把网络/后端错误也显示成「该时间段暂无历史数据」，误导用户。

**建议**：`api` 层统一 `try/catch` + 非 2xx 抛错；历史查询区分「空结果」与「查询失败」两种状态。

---

### ⚪ P3 — 代码质量：`query` 的 `useCallback` 依赖不完整（stale closure 隐患）

**位置**：`App.tsx` 第 710–730 行，`query` 内部读取了 `registers` 与 `selectedRegisters`，但依赖数组只有 `[device.id, start, end, canQuery]`。

**说明**：`selectedRegisters` 来自 `selected` state，变化时不会重建 `query`，理论上「先少选寄存器 → 触发 `query` 重建 → 再扩大选择」方向会用到旧选择计算值。实际因默认全选 + 被 P0 时间戳问题掩盖，未在 UI 上稳定复现，但属于明确的隐患，**建议把 `registers`/`selectedRegisters` 加入依赖或改为直接读取最新 state**（一行改动，低风险）。

## 五、易用性评价

**做得好的**：
- 视觉风格统一（深色/浅色主题、CSS 变量），与 DSH 风格一致。
- 实时数据表格清晰：地址/别名/类型/值，别名和类型可就地编辑，体验顺滑。
- 主题与语言切换即时生效且持久化（localStorage）。
- 工作区「文件夹树 + 最近使用」符合既有设计，切换工作区后状态正确重置。

**最影响体验的三件事（建议优先改）**：
1. 历史页多分组错位（P0）—— 数据看起来是「缺一半」。
2. 移动端布局（P2）—— 手机上基本没法用。
3. 删除无确认（P1）—— 配置有被误删风险。
