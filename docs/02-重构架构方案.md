## 1. 范围与目标

重构现有 Monitor 平台（`/home/leo/modbus_tcp_monitor`，树莓派 192.168.90.34），实现其全部现有能力，并采用 DSH「一切皆插件」的理念组织代码。

**在范围内**（现有 Monitor 能力 + 重设计）：

- Modbus TCP 主站轮询设备、状态可视化、历史数据留存、日志；
- WebSocket 实时推送；
- master / slave 双模式（slave 引擎作为 Modbus 从站模拟器）；
- OTA / IAP 固件升级；
- MBS / MBP 寄存器文件导入导出、CSV / XLSX 数据导出；
- 数据持久化重设计（热内存缓冲 + 列存 + 降采样）。

**明确不在范围内**：

- 结构化语义层（scale / unit / enum 字段）——不做，AI 阶段的语义由外部整理成 Excel 提供；
- 写真机鉴权 / 审批——暂不做，仅预留审计事件钩子；
- 设备类型模板——保持「每台设备独立配置寄存器」。

**目标**：数据采集与可视化能力不退化；代码组织改为插件化，边界清晰、可独立替换；持久化更高效，支撑 AI 分析层。

## 4. 总体架构

### 4.1 插件化范式（Cordis 五理念）

Monitor 重构完全照搬 DSH 的 Cordis 范式（见 `reference/deepseek-harness-master/docs/cordis-primer.md`）：

1. **插件 = 实现 Service 的对象**：函数 + 可选 `inject` / `apply(ctx)`，或 Service 子类。
2. **context 是服务仓库**：服务挂在 `ctx.<key>`（如 `ctx.modbus`、`ctx.store`），按 key 找服务，不 import 具体实现。
3. **`inject` 声明依赖**：加载顺序由服务依赖决定，不手写启动顺序。
4. **类型化事件通信**：`emit / waterfall / parallel / serial`。
5. **注册都是可逆 effect**：`ctx.effect()` / `ctx.on()`，卸载自动回滚。

### 4.2 目录结构

```
probestation/
  apps/
    cli/            # 启动入口：加载 cordis.yml，装配插件
    web/            # React 前端（Vite）
  packages/
    core/           # 配置 schema、全局 ctx、日志
    modbus/         # Modbus TCP 驱动（master + slave 的抽象与实现）
    poller/         # 轮询引擎
    slave/          # 从站模拟器
    store/          # 持久化（ctx.store 接口 + DuckDB 引擎）
    sink/           # 数据出口（CSV/XLSX 导出）
    rule/           # 告警规则引擎
    api/            # REST API
    ws/             # WebSocket 推送
    ota/            # IAP 固件升级
    importer/       # MBS/MBP 解析导入
    client/         # 前端 UI 插件（ui-layout / panels / ...）
  config/
    cordis.yml      # 插件装配
  docs/
```

### 4.3 插件边界与数据流

```
                 ┌──────────────┐
   Modbus TCP ──▶│   modbus     │  ctx.modbus（驱动抽象）
   设备(真机)     │  (jsmodbus)  │
                 └──────┬───────┘
                        │ read/write
                 ┌──────▼───────┐
                 │    poller    │  ctx.poller（轮询引擎，inject modbus + store）
                 └──┬────────┬──┘
                    │ result │ status
          ┌─────────▼───┐  ┌─▼────────────┐
          │    store     │  │      ws       │  ctx.ws（WebSocket 实时推送）
          │  (热缓冲+    │  └───────────────┘
          │   DuckDB)    │
          └─────────┬───┘
                    │ query / latest
          ┌─────────▼───┐    ┌────────────┐
          │    api       │    │   importer  │  MBS/MBP 导入 → 配置
          │  (Fastify)   │    └────────────┘
          └──────────────┘
                 │
          ┌──────▼──────┐    ┌────────────┐
          │    client    │    │  slave /    │  从站模拟（inject modbus）
          │ (React 前端) │    │  ota / rule │
          └──────────────┘    └────────────┘
```

依赖方向：上层插件通过 `inject` 声明对下层服务的依赖；跨模块通信走类型化事件；任何实现（jsmodbus、DuckDB、Fastify）都被包在 Service 接口后，可替换。

## 5. 插件契约

每个插件暴露一个或多个 Service 于 `ctx`，用 schemastery 定义 Config。以下为接口骨架（TS 签名示意，Phase 1 细化）。

### 5.1 `core` —— 全局配置与上下文

- Config：`host`、`port`、`db_path`、`data_retain_days`、`default_poll_interval_ms`、`tz`、`log_level`。
- 提供 `ctx.config`（全局配置对象）与日志。

### 5.2 `modbus` —— Modbus 驱动

- Service `ctx.modbus`：抽象接口 `BaseModbusDriver`（对齐现有 Python 版）：
  `connect / disconnect / read_holding_registers / read_input_registers / read_coils / read_discrete_inputs / write_register(FC06) / write_registers(FC16) / write_coil`。
- Provider：`jsmodbus` 实现 master；`slave/` 插件提供 slave 侧（`ModbusTcpServer`）。
- 未来加协议（RTU、其它库）＝新增 provider，不碰上层。

### 5.3 `poller` —— 轮询引擎

- Service `ctx.poller`：`connect(objectId) / disconnect(objectId) / write_value(...) / is_connected(objectId) / set_group_paused(...)`。
- 事件：
  - `poller/result`（emit）：每次轮询结果（object_id, 寄存器列表 + raw 值）。
  - `poller/status`（emit）：连接状态变化。
  - `poller/group-error`（emit）：组读取失败。

### 5.4 `store` —— 持久化 sink

- Service `ctx.store`：`write_batch(points) / query(range) / latest(objectId) / downsample() / retention()`。
- 引擎＝DuckDB（见 §6.2）；接口使 SQLite / TDengine / InfluxDB 可替换。

### 5.5 `sink` —— 数据出口

- 事件订阅 `store` 数据，提供 CSV / XLSX / Parquet 导出（替代现有 export_service）。

### 5.6 `rule` —— 告警规则（从零做）

- Service `ctx.rule`：`evaluate(objectId, results)`。
- 事件 `rule/trigger`（emit）：命中告警（规则、设备、寄存器、值、阈值）。
- Config：规则定义（sche mastery schema：条件、阈值、动作）。

### 5.7 `api` —— REST API

- 移植现有端点到 Fastify 路由，路径保持兼容（`/api/monitor_objects`、`/api/groups/{gid}/registers`、`/api/registers/{id}/write`、`/api/data/query` 等），前端无需大改即可对接。

### 5.8 `ws` —— WebSocket

- Service `ctx.ws`：`broadcast_data / broadcast_status / broadcast_stats`。订阅 `poller/result` 与 `poller/status`。

### 5.9 `ota` / `importer` / `slave`

- `ota`：IAP 固件升级流程（inject `ctx.modbus`）。
- `importer`：MBS/MBP 解析 → 生成 group/register 配置。
- `slave`：`ModbusTcpServer` 从站，供测试；inject `ctx.modbus`，数据经 `ctx.store` 回写。

## 6. 数据模型

### 6.1 配置元数据（SQLite）

沿用现有结构（每台设备独立配置，无语义层字段）：

- `monitor_objects`：id, name, ip, port, remark, is_active, data_retain_days, timeout_ms, sort_order, mode(master|slave), slave_port, poll_interval_ms。
- `register_groups`：id, object_id, name, slave_id, function_code, start_address, quantity, poll_interval_ms, mode(read/write/read_write/disable), is_active。
- `registers`：id, group_id, object_id, alias, function_code, start_address, quantity, data_type(int16/uint16/int32/float32/…), remark, sort_order。
- `logs`：日志（含将来审计事件的落点）。

### 6.2 时序数据（DuckDB，重设计）

现状硬伤（1s 轮询 × 50~60 寄存器 × 8 设备 × 30 天 ≈ 10 亿行、行式 SQLite、无降采样）的替代：

1. **热层（内存）**：每寄存器一份 latest 快照 + 近 1 小时环形缓冲。`/latest`、WS 推送、图表近期点都走内存，不打盘。
2. **冷层（DuckDB 列存）**：`poll_data(object_id, register_id, ts, raw_value, quality)`，列式 + zstd，append-only，批量写入。
3. **批量写**：轮询值攒批（每 5s 或每 1000 行）一次 INSERT。
4. **降采样 + 保留**（`store` 内建或 `tasks/cleanup`）：0–24h 保 1s 原始 → 1–7 天降 1min 聚合（min/max/avg）→ 7–30 天降 5min → 超 30 天删除。

`decoded_value` 不再落库（由 raw + 类型现算）；导出走 DuckDB 原生 CSV/Parquet（Parquet 同时作为 AI 层输入）。

## 7. AI 测试层（复用 DSH）草图

AI 层独立于监控重构，但**运行时直接复用 DSH**，不重复造 agent 机制：

1. **语义输入**：外部整理的 Excel（寄存器地址 → 单位/缩放/枚举/描述）作为 agent 上下文，不进平台 schema。
2. **能力暴露**：把 ProbeStation 的能力（读实时快照、查历史区间、写寄存器）做成 DSH 的 tool / Service 契约，AI 测试用例即 DSH agent。
3. **闭环**：读状态 → 判读 → 控制 → 验证，由 DSH 的会话 / goal 机制驱动。
4. **部署分层**：边缘（树莓派）跑采集 + 监控；DSH / agent 跑在算力足够处，经 API / WS 或直连 Modbus 接入。写控制前接入审批（鉴权/审批预留点，见 §9）。
