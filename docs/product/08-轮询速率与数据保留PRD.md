# 轮询速率与数据保留 PRD

> 状态：v1.0 · 日期：2026-08-16
> 读者：开发侧（平台实现）+ 产品侧。
> 前置：`05-Agent调试接口PRD`（MCP 接口现状）、`06-开发任务与交接`（开发任务）。
> 定位：给平台补两件「快采样调试」缺的能力——① **按设备可调轮询速率（最小 1ms）**；② **历史数据保留时长可配置**。

---

## 1. 背景：为什么现在要这两件

调试场景里，有的测试需要**很快读到数据**（如抓瞬态、看波形、调 PWM/电机响应），而默认 1s 一轮的采样太粗，跟不上。

这带来两个直接问题：

1. **速率不够**：现状最快只能 1 秒采一次，读不到"很快"的数据。
2. **数据会爆**：一旦采样变快，落库量暴涨（架构文档点名：1s × 60 寄存器 × 8 设备 × 30 天 ≈ 10 亿行）。所以"能快"的同时必须配套"能只保留多久"，否则磁盘/查询很快被拖垮。

两个需求是一对，要一起做。

---

## 2. 现状核实（源码级，2026-08-16）

| 层 | 现状 | 结论 |
|---|---|---|
| 全局轮询循环 | `poller` 里 `setInterval(tick, config.pollIntervalMs)`，默认 1000ms，**启动写死、运行时不可改** | 要动它，才能支持 <1s 采样 |
| 组级 scan rate | `register_groups.poll_interval_ms`（默认 1000），`create_group`/`update_group` 已带此参数 | 有，但受全局 tick 限制，实际最快也只能 1s 一次 |
| 设备级速率 | `monitor_objects` **无** `poll_interval_ms` 字段 | 缺 |
| 数据保留 | `dataRetainDays` 仅作为 core 启动日志打印（`retain=Nd`），**无任何清理逻辑** | 缺（Phase 5 未实现） |

**关键坑**：现状是「全局每 1s tick 一次，tick 里再判断哪些组到期」。所以哪怕把组级 `poll_interval_ms` 设成 100ms，全局还是 1s 才检查一次，**实际最快 1s**。要读"很快"，必须让全局调度能更快，并且按设备独立调度。

## 3. 需求一：按设备可调轮询速率（最小 1ms）

### 3.1 数据模型

`monitor_objects` 新增一列：

| 列 | 类型 | 默认 | 约束 | 说明 |
|---|---|---|---|---|
| `poll_interval_ms` | INTEGER | 1000 | ≥ 1 | 该设备所有组的统一采样周期 |

### 3.2 采样周期语义（定死，避免开发歧义）

> **设备级 `poll_interval_ms` 是该设备下所有组的统一采样周期（主控制）。**
> 组级 `poll_interval_ms` 字段**保留**（向后兼容，不删数据），但采样调度**改读设备级**，不再读组级。
> 若未来确需"同设备内个别组单独更快"，再单独做组级细分——本期不做，避免两层混淆。

一句话：**按设备设一个值，这台设备所有寄存器都按这个周期采。**

### 3.3 调度（实现目标，细节开发定）

- 全局循环不能再写死 1000ms：**tick 间隔 = 所有启用设备的最小 `poll_interval_ms`**（或按设备独立 `setTimeout` 调度，等价）。
- 保证：设了 1ms 的设备**尽可能快**地采，且**不影响其它设备的周期**。
- 采完一轮后，设备按其自身周期判断下一次是否到期（现状的 `lastPoll` 逻辑保留，但比较基准换成设备级周期）。

### 3.4 MCP 工具

| 工具 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `set_poll_interval` | `device_id: number, poll_interval_ms: number` | `{ ok: true }` | 设设备采样周期；`poll_interval_ms ≥ 1`，越界报错 |
| `get_device_health`（扩展） | 已有 | 加字段 `poll_interval_ms` | 透出当前生效周期，agent 能读到 |

### 3.5 诚实标注（1ms 是下限，不是能达到的速率）⚠️

1ms 是**允许设置的下限**，但**物理上采不到 1ms**：

- **Modbus 一帧往返本身就几 ms**：TCP 局域网典型 1~5ms/帧；RTU 串口受波特率限制，9600 下读一帧约 40~50ms。
- 所以"设 1ms"的实际效果 = **"尽可能快地采"**，真实采样率 = `max(1ms, 通信往返时间)`。
- **高频 tick 的代价**：1ms 级的调度会高 CPU、可能挤压事件循环（影响 UI/其它请求）。实现时要注意不让一台快采样设备拖垮整个进程。

> 这条要写进 MCP 工具描述，让 agent 知道「设 1ms ≠ 真 1ms」，避免它对数据密度产生错误预期。

## 4. 需求二：历史数据保留时长可配置

### 4.1 保留时长

- **粒度**：全局默认 + **按设备可选覆盖**（快采样设备往往需要更短的保留）。
  - 全局：一个默认保留时长。
  - 设备级：`monitor_objects` 加 `data_retain_seconds`（NULL = 跟随全局）。
- **单位**：秒（MCP 机器接口）；Web UI 用人友好下拉。

| 表达 | 值 | 说明 |
|---|---|---|
| MCP / 存储 | 秒（number） | `0` = 永久保留 |
| Web 下拉 | 1h / 6h / 24h / 7d / 30d / 90d / 永久 / 自定义 | 映射到秒 |

- 默认：全局 30 天（对齐现状 `dataRetainDays`）。

### 4.2 清理机制

- 定时清理：`DELETE FROM poll_data WHERE ts < now - retain`（按设备覆盖时加 `object_id` 条件）。
- 频率：启动时 + 定时后台清理（建议每 5~10 分钟），避免长期膨胀。
- 注意：快采样下**热内存缓冲**也会快速膨胀，实现层需关注 flush 频率/缓冲上限（避免内存先于磁盘爆掉）。

### 4.3 MCP 工具 / 设置

| 工具 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `set_data_retention` | `retention_seconds: number, device_id?: number` | `{ ok: true }` | `0`=永久；缺省 `device_id` 设全局，否则设该设备覆盖 |
| `get_data_retention` | `device_id?: number` | `{ retention_seconds }` | 查当前生效保留时长（设备覆盖优先于全局） |

Web「设置」页同步加保留时长下拉（可选按设备覆盖入口）。

## 5. 两个需求的关联（为什么一起做）

快采样（需求一）是数据暴涨的放大器，保留清理（需求二）是它的泄压阀。**只做快采样不做保留 = 磁盘会被快速填满；只做保留不做快采样 = 快采样需求仍落不了地。** 建议同批开发、同批验收。

---

## 6. 验收标准

### 需求一（轮询速率）

- [ ] `set_poll_interval(device, 100)` 后，该设备实际采样周期约 100ms（非 1s），其它设备不受影响。
- [ ] 设 `poll_interval_ms=1` 不报错、平台能跑，且 `get_device_health` 透出该值。
- [ ] 设非法值（0 / 负数 / 非整数）明确报错，不静默改值。
- [ ] 一台快采样设备不拖慢/拖垮其它设备或 UI。

### 需求二（数据保留）

- [ ] `set_data_retention(600)`（10 分钟）后，超过 10 分钟的历史数据被自动清理。
- [ ] `device_id` 覆盖生效：某设备设更短保留，只清它自己的旧数据。
- [ ] `retention_seconds=0` 表示永久，不清理。
- [ ] 清理不误删"仍在保留期内"的数据（时间边界正确）。

---

## 7. 风险与开放问题

1. **1ms 调度的 CPU/事件循环代价**：高频 tick 可能影响 UI 和其它服务，实现需限流/节流（开发侧定阈值）。
2. **RTU 串口的物理上限**：9600 波特率下读一帧 40~50ms，串口设备设 1ms 无意义——是否要在设备配置层提示"当前传输方式的物理上限"，待定。
3. **清理期间查询一致性**：`DELETE` 与并发查询/写入的竞态，开发侧处理（可参考 DuckDB 事务）。
4. **组级 `poll_interval_ms` 的既有数据**：本期采样调度不再读它，若有人曾依赖组级速率，需在交接说明里标注（产品侧判断：现状无人真用，可安全忽略）。
