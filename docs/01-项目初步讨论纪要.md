# ProbeStation（砺台）项目初步讨论纪要

> 状态：草案 v0.1 · 日期：2026-08-13
> 性质：立项前初步讨论记录，作为后续 PRD / 架构设计的输入，非定稿。

## 1. 项目定位

ProbeStation（砺台）是一款面向嵌入式设备的**观测与测试平台**。

- 当下能力（继承自现有 Monitor 平台）：Modbus TCP 轮询设备、状态可视化、历史数据留存、告警、日志。
- 未来能力：接入 AI，用 AI 对嵌入式设备做自动化测试 —— 读状态 → 判读 → 控制 → 验证。

一句话定位：**设备试验台（probe station）+ 测试大脑（AI）**。监控是数据底座，AI 测试是大脑与核心卖点。

## 2. 命名

| 类型 | 名称 | 说明 |
|---|---|---|
| 中文产品名 | 砺台 | 「砺」=磨砺/反复试验，「台」=bench/station |
| 英文/代码名 | ProbeStation | 半导体「探针台」隐喻：用探针戳芯片测好坏 ≈ 用 Modbus 戳设备测好坏 |
| npm scope 建议 | `@probebench` 或 `@probe` | 待查重 |
| 技术代号（可选） | EmbHarness / DeviceHarness | 借 DSH 的 harness 语义，不建议对外 |

命名原则：

1. 不绑定具体协议（不写 Modbus）。
2. 不绑定具体产品（不写冰沙机）。
3. 不把 AI 写进产品名（AI 是方法不是目的，易过时、易过度承诺）。
4. 工程名（英文）与产品名（中文）分离。

## 3. 背景与动机

### 3.1 现有系统（Monitor 平台）

- 地址：http://192.168.90.34:3000（内网）。
- 技术栈：Quasar / Vue 前端 + Node 后端，后端作为 Modbus TCP 主站。
- 现状：已轮询 8 台设备、留存 30 天历史、提供完整 REST API、日志可查。

### 3.2 重构动机（真实痛点待最终确认）

1. 加新设备/新协议麻烦 → 驱动插件化。
2. 加新页面/新面板麻烦 → UI 插件化。
3. 加新告警/新数据出口麻烦 → 规则 / sink 插件化。
4. 代码结构乱、难维护 → 模块边界重构（未必需要上插件框架）。
5. 为 AI 测试打地基 → 建议做成独立薄适配层，不并入监控重构。

## 4. 现有系统调研发现（Monitor 平台实测）

### 4.1 数据模型

- `monitor_object` = 设备（Modbus TCP master 连接）。
- 每台设备下有 `group`（寄存器组）= 地址区间（start_address + quantity + function_code）。
- 每个 group 下有 `register` = 单点（alias、address、data_type int16、quantity）。
- 设备 id=9 = 雪融机（LR3 冰沙机，192.168.90.32:8899），寄存器表已与固件 `monitor.h` 1:1 对齐（47 只读 + 5 读写 + 7 手动测试）。

### 4.2 现有 REST API（实测可用）

| 端点 | 用途 |
|---|---|
| `GET /api/monitor_objects` | 设备列表 |
| `GET /api/monitor_objects/{id}/groups` | 寄存器组 |
| `GET /api/groups/{gid}/registers` | 寄存器定义 |
| `GET /api/monitor_objects/{id}/latest` | 实时值快照（int16 有符号解码 + quality） |
| `GET /api/data/query?...` | 历史时序（30 天） |
| `POST /api/registers/{rid}/write` | 写寄存器 `{value, method: single|multiple}` |
| `POST /api/monitor_objects/{id}/toggle` | 暂停/恢复轮询 |
| `GET /api/monitor_objects/{id}/connection-state` | 连接状态 |
| `GET /api/logs` | 日志 |

### 4.3 发现的 3 个差距

1. 手动测试段缺 2 个寄存器（`0x2007 forward_rpm`、`0x2008 reverse_rpm`）。
2. 平台未做缩放（只做 int16 有符号，不做 0.1°C / 0.001A），需在语义层补。
3. 写寄存器须确认走 FC10（固件只开 FC03 + FC10，FC06 关闭）。

## 5. 目标架构（仿 DSH 插件化）

### 5.1 借鉴 DSH 的部分

- 插件化骨架（Cordis 或类似运行时）：驱动插件 / sink 插件 / 规则插件 / UI 插件。
- 强类型配置：寄存器表、设备定义、告警规则用 schema 校验（DSH 用 schemastery）。

### 5.2 不照搬的部分

- agent 专属机制（工具契约、沙箱升级、subagent、workflow、goal）—— 本软件是固定逻辑，不需要。
- 100+ 包粒度 —— 10 个左右模块边界即可。
- 前端技术栈 —— 不必为「像 DSH」换成 React + Vite；Quasar 本身适合工业仪表盘，除非有它解决不了的痛。

### 5.3 AI 测试层（独立）

- 通过现有 REST API 接入，做成独立薄适配层（transport + semantic + agent）。
- 不要把 AI 测试并入监控平台重构，避免最贵且不必要的耦合。

## 6. AI 测试嵌入式设备的构想

三层结构：

1. 传输/数据层：现有 Monitor REST API，或直接 Modbus TCP（FC03 / FC10）。
2. 语义层：寄存器 id / 地址 / 别名 × 固件 monitor.h 的单位 / 缩放 / 枚举（唯一真源是 monitor.h，非 CSV）。
3. 智能层：AI 生成用例 → 判读 PASS/FAIL → 诊断 → 自适应下一步。

已知风险：

- 慢用例（制冷 240s 消抖 / 再辉 60s / 总超时 70min）不适合 AI 实时闭环，应脚本化 + AI 事后判读。
- 有符号 + 缩放需正确处理（否则 -15°C 会读成 654°C）。
- 写寄存器属控制真机，需审批与授权。

## 7. 关键决策（本次讨论已定）

- 产品名：砺台 / ProbeStation。
- 分层：监控平台保持稳定，AI 测试独立适配。
- 语义真源：固件 monitor.h（非 modbus_register_map.csv，已过时）。
- 架构参考：仿 DSH 的插件化骨架，不仿其 agent 机制与前端技术栈。
