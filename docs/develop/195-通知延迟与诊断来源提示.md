# 通知延迟与诊断来源提示

## 模拟证据与边界

使用实际PollingEngine的配置变更监听、内存调度缓存、驱动绑定与只读方法，模拟TCP/RTU通知丢失及延迟，共4组。没有启动调度定时器、连接真实设备或打开数据库。

1. 旧配置A已连接，通知被扣留后，缓存推送仍可能保持true；按当前配置B查询连接则为false，统计/捕获拒绝旧驱动。
2. 夹具显式建立模拟B驱动后，缓存A又可能推送false，而当前配置B查询为true。统计/捕获读取器只按设备ID/通道核对，因此仍持A配置的页面可以接受B报告为ready；成功读取不证明报告与本页配置版本绑定。
3. 延迟通知交付后，原刷新调度缓存逻辑读取最新B配置，推送可以恢复与查询一致。这不是可靠通知保证；从未收到的消息、页面配置刷新、ABA或同地址物理设备替换依然没有版本确认。

这是受控模拟，不是对现场设备故障的判断。不得把connected真假直接当作来源已验证或物理设备在线/离线的充分依据。

## 最小体验改进

原通信统计、捕获的成功状态没有明确说明本页配置版本未绑定，旧渲染在新断言处失败。现在在通信统计、原始捕获、设备概览及展开的设备列表显示中英文提示：“后台报告未绑定本页配置版本；通知可能延迟或遗漏，需核对来源。”状态徽标及已收到报告的侧栏圆点补充相同说明；未收到报告/页面断线时圆点仍使用既有“连接状态未核实”。

提示在成功/失败/无数据等状态下均存在，不将通知延迟称为硬件故障，不隐藏记录或改变布尔状态、采集、缓存、连接、清空及写入。未新增预检、刷新请求或自动重连；重新读取也不被描述为能锁定版本。
