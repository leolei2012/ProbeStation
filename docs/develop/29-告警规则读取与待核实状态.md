# 告警规则读取与待核实状态

2026-11-06，基线`3a76357`。本轮只开发、模拟验证和本地提交，不更新运行服务、接触实机或修改真实数据。

## 证据与选择

基线`AlarmPanel`不使用`useAlarmRules.ready`：初次`rules=[]`便显示“未设置规则”；读取失败时保留旧规则，也继续按旧列表显示“未触发”。对基线组件做纯SSR复现，首个摘要确实是`alarmNone`，全程未运行effect或网络请求。原读取将响应直接交给`rules.filter`，非数组会报错，异常/未知比较符也可能被当作正常未触发。请求没有期限，每10秒定时器可以叠加未结束的GET。

本轮优先修复规则读取是否完整这一前提，没有改阈值、采样质量/批次/来源校验或自动告警策略。“从当前告警打开相邻历史”是有用的后续候选，但在摘要可信状态明确前不扩大功能。

## 现在的行为

- 每个现有规则查看器有独立读取模型；构造和订阅不发请求，钩子沿用既有`GET /api/rules`与10秒轮询。未新增API或共享后台缓存。
- 首次未读、显式写后待核实、读取失败时摘要明确待核实；在途读取显示“正在读取规则”，不展示当前正常/无规则结论。只有合法完整响应后才可显示“未设置规则”“未触发”或按既有数据规则判断。
- 已读后的正常轮询使用预留短状态行，不每10秒展开完整提示框；首次/失败/待核实时才显示详细说明。实际窄屏布局仍待浏览器验收。
- 失败保留上次完整规则及准确UTC读取时刻，不接受部分列表；计数明确是接口返回的全设备规则。旧规则仍可供核对/已有筛选使用，顶部旧规则算出的提示有保留标注，数量为0不证明当前无告警。
- 实时筛选保留已载入规则和原计数语义，规则未核实时提示不完整，并提供只读重试；在后台刷新期间标明按上次完整规则计算。
- GET整体（含解析）30秒超时并取消客户端请求；即使提供者忽略abort也解除等待。周期刷新合并在途请求，不反复重置期限；显式重读/规则变化事件可以替换旧请求。晚到成功/失败、切换设备和effect清理后的回调不能覆盖新状态。
- 失败/未核实或读取中不能提交保存、编辑或删除确认，草稿输入仍保留。原显式保存/删除只执行一次，开始后使本查看器规则状态待核实；读回也经完整校验及GET期限，成功才恢复已读取。失败提示先重读核对，重读只发GET，不自动重复写入。尝试结束通知其他查看器只读刷新，通知不表示写入一定成功。

## 规则契约与边界

核对当前`GET /api/rules → ConfigStore.listRules`：JSON数组，每行包含正安全整数`id/registerId`、六种已有比较符、有限数字阈值和字符串/null提示。拒绝重复规则ID、字符串数字、缺失字段、非有限阈值或异常行，不悄悄删规则后宣称完整；空数组是合法空配置。只投影已知字段并冻结快照，不带入任意扩展字段。阈值不增加上下限、不舍入，零/负数/小数及现有大数语义保留。

读取成功只表示那次收到完整格式的配置，不证明服务端之后没有变化、规则对应点位仍存在或采样可信；现有点表/值/来源/批次检查继续生效。服务端写入策略、真实数据库、告警记录和硬件均未修改。

独立查看器仍按原方式各自轮询，不承诺同一时刻共享事务快照。GET取消不保证停止服务端工作。写请求自身的时长、CAS、持久化幂等和跨客户端重复操作保护未在本轮实现；响应丢失/读回失败时保守要求核对，不证明未写入，也不自动回滚。重新读完不会自动改写已有草稿；用户需对照列表核实后再操作。
