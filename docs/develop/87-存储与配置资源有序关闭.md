# 存储与配置资源有序关闭

基线`426a79a82a68f31fc70420ac09733d12e5b36463`，开始时工作区干净。本轮处理根上下文卸载后仍存活的存储定时器、DuckDB和SQLite连接，继续在独立源码/依赖副本、临时/内存夹具中验证，没有执行主入口或触及真实数据。

## 顺序不能由框架猜测

Cordis当前版本根卸载并发执行disposables并记录错误。最初候选“嵌套effect，先撤销provider再关闭数据库”在真实根上下文中被隔离证明推翻：消费者还在等待，存储及配置的关闭回调已经执行。该方案未接入。

本轮使用按**实际对象身份**登记的资源依赖，不用名称、ID、时间戳或provider撤销作为释放屏障。每个消费者的退出函数只运行一次并共享同一个Promise，正常和失败结果都可重复观察。配置库等待存储及其它消费者，存储等待API、MCP、轮询和从站；这些消费者等待自身已接受的工作。框架即使并发调用所有退出函数，等待关系仍然成立。关闭成功的消费者解绑，失败结果保留；自定义或独立构造的消费者没有登记时不具备这层保证。

主要顺序是：停止新采样/入口→等待接受工作与消费者清理→等待存储既有查询、写入、初始化/重开→尝试最终flush→主连接与实例→最后SQLite。原始查询过滤和样本序列化格式没有业务变更。

## close契约及失败处理

- `DuckDBStore.close()`立即停止两个定时器，拒绝新写入/查询/清理/重开，撤销导出句柄，落盘元数据返回既有`{version:1,available:false,objectId}`。它等待消费者、已接受的读取（含独立曲线连接）、排队写入和已经开始的reopen，再尝试最终flush，最后分别尝试关闭主连接及实例。
- `ConfigStore.close()`先等待登记的消费者和存储，再撤销快照/录制租约并关闭SQLite；恢复录制周期和存储清理完成前，SQLite仍保持打开。新的reopen拒绝；普通活动API契约、库schema及存储字段均未改变。
- 两个close都返回缓存的同一Promise，失败不会通过再次调用盲目重写或重复释放。只有一个错误时保留原对象；多个错误保留在AggregateError.errors（按原对象去重）。某一步失败不跳过其余可执行清理。初始化的schema/connect错误与同时发生的native close错误也保留，不再被finally里的错误覆盖。
- 最终flush失败不清空缓冲；先保留store引用，失败后可用`getPersistenceStatus().pendingRows`和`getPendingPoints()`取得独立样本副本。副本只在内存，不是持久恢复日志，进程强杀仍可能丢未落盘点。事务结果不明时不得自动重放，以免重复或伪造数据。这里不新增自动重试、磁盘spool或业务写入补偿。
- 即使native close报告失败，状态仍不可就绪，不伪装资源释放成功；相应错误可通过缓存的close结果核对。已经关闭的对象不能复活，恢复应创建新实例。

不能只以`await ctx.fiber.dispose()`返回判断所有清理成功，因为框架会记录部分错误。需要结果的调用者应预先保留store/config引用，卸载后再次检查各自close的缓存结果；这不会再次执行flush或native关闭。不能吞关闭错误后无条件process.exit。

## 相邻消费者必须一起处理的原因

- API复用已验证的Fastify关闭流程，并把同一退出Promise登记到配置、存储与轮询器。助手后台分析/压缩在preClose先abort，再等待其Promise完成；只abort而未等待的基线已用延迟响应mock复现并修复，避免HTTP关闭后后台仍访问配置。没有调用模型服务。
- Poller进入终止状态后先quiesce：停止定时调度并撤销迟到帧的生命周期，拒绝重新startAll、pollOnce或取得新driver，保留已接受工作仍需的通道；等待API/MCP/OTA相关消费者后再disconnect。普通stopAll仍可用于原有重启流程，只有终止清理会设置不可复活状态。全部驱动都尝试关闭，断连失败保留原错误，不再静默吞掉。DeviceSlaves同样缓存终止结果；先等待reconcile，失败仍尝试每个从站，并汇总错误。
- 从站插件此前没有声明配置/存储依赖，不能依赖provider通知解决其顺序。本轮直接绑定捕获的实际资源，先停止设备级从站，再分别尝试TCP和RTU清理，一个失败不跳过后续步骤。
- MCP跟踪已接受SDK connect、HTTP/tool Promise，停止新请求/工具入口；关闭录制计时器、transport和HTTP，再等待既有工作。监听启动的error会报告并保留到关闭结果，关闭等待启动结果，防止先关后迟到bind。请求头在关闭前到达、body在关闭后完成也拒绝503，不新建SDK服务器或抛出未处理异常（此边界已先失败后通过）。正常工具形状保持不变；监听失败时/ready仍仅代表sample-storage，不变成全系统健康检查。
- Recorder终止自己的计时器和接受入口；按原有来源/租约规则归还周期，异常仍清理剩余计时器，不改并发周期恢复策略。
- OTA关闭只阻止新升级并等待已接受Promise，不发额外协议命令，也不引入强制中断/断电策略。关闭中的已接受升级结束后不再resume/reconnect已退出的轮询器。真实升级退出未测试；模拟只验证等待与无额外重连。

## 隔离回归

新增test-store-lifecycle（先在旧基线失败）和test-runtime-close，加入显式安全白名单：

1. 真实临时DuckDB最终flush、关闭后重开，验证值、batchId、slaveId无损；关闭中拒绝新操作，重复调用同一Promise，两个定时器确实销毁。
2. 已接受主连接查询和独立流式曲线暂停，关闭必须等待释放；COMMIT中的reopen与关闭竞争，已接受操作完成后才释放当前连接，旧文件样本仍完整。重开也等待旧读取完成，不能再将它当作强关未结束SQL；旧导出句柄测试据此补充“读取释放前禁止关连接”断言，并继续验证迟到结果/错误均拒绝。
3. 慢初始化、初始化失败、SQLite schema失败与其cleanup失败、DuckDB connect与cleanup同时失败；原错误身份可核对。
4. INSERT、writer close、主连接close及实例close同时失败，所有可执行清理都尝试，原错误都保留；待写缓冲及取回副本不被破坏，重复close不重复插入。
5. 真实Cordis并发根卸载中故意暂停消费者，配置/存储连接必须仍打开；释放后观察到消费者→存储→配置。消费者失败也不跳过两库释放，缓存结果仍能找到原错误。另覆盖驱动断连错误和从站reconcile/逐个stop的多处失败。
6. 使用真实config/store/poller/Sink/importer/OTA/MCP/slave/API，只有设备驱动、HTTP/TCP监听及OTA接受Promise是纯mock。实际MCP SDK通过内存HTTP流完成initialize和session建立；实际MCP工具调用暂停、模拟OTA工作暂停，根卸载必须等待，随后所有数据库/定时器/模拟监听关闭，旧health/ready拒绝新请求；MCP bind失败和从站close失败仍清理数据库且保留原错误。另覆盖迟到body503及助手mock收到abort后仍延迟结束，关闭必须等其任务完成并持久化停止状态。
7. 此套件直接启动的仅是隔离内存配置上的mock PollingEngine调度，以验证quiesce先发生；未执行主入口，也不启动真实采集。网络listen/connect、串口open/write/list及fetch都有守卫，最终拒绝计数必须为0。没有OS端口、串口枚举或模型调用。

最终独立候选`npm run check`退出0：仓库配置的前后端类型检查、构建/按需包边界及104组安全回归全部通过，包含新的存储/运行期退出套件、助手后台等待和更新后的导出句柄回归。首轮完整检查因旧句柄测试先等待reopen、后释放读取而出现未完成await（退出13）；补充禁止早关连接的断言并调整释放顺序后，最终候选重新完整执行，未将首轮或历史结果算作本次通过。

## 尚未覆盖和使用限制

- 主入口仍未接SIGINT/SIGTERM及统一启动失败finally，本轮不改变默认Ctrl+C/崩溃语义；只有调用这些关闭方法或卸载上下文时上述流程才执行。真实进程退出信号、强杀、OS监听排空、设备/串口驱动和真实升级未验收。
- 挂起的native读取、transport或OTA Promise可能延迟关闭，没有加入任意超时后强关连接/丢缓冲的策略。失败时native资源是否已实际释放可能未知，以错误为准。
- 正常configured typecheck范围仍按仓库现状；额外把整个MCP SDK入口纳入的类型推导耗时过长，已中断本轮自有检查，未记为通过。新增退出路径另有真实模块运行回归，不能替代该额外静态覆盖。没有安装依赖。
- 自定义provider/消费者须显式登记资源关系，绕过公共方法调用私有db.close/closeSync不受保护；非主程序使用的旧Workspace管理路径未作为真实工作区退出验收。新闭环不是生产数据库迁移或发布验证。

未推送、部署、重启在用服务、打开真实库、读写仪器或调用外部模型。
