## 已核实的契约与问题

基线`c0320fdfd638ca1499b1f2e8d6d09b50492a1cfe`，开始时工作区干净。继续只用新建临时目录、合成SQLite/DuckDB和内存ConfigStore，不读取真实数据，不启动CLI、采集、串口、模型或网络监听。主入口及信号行为保持不变。

复现：合法JSON包含Number.MAX_SAFE_INTEGER保留秒数，可解析、恢复和持久化；旧cleanup用`new Date(now - seconds * 1000).toISOString()`计算截止点，会抛`RangeError: Invalid time value`。构造后的启动清理报告异常，公共cleanup重试仍失败；前面的设备可能已清理，后面的设备及全局规则未执行。修复前新增5项中2项因该错误失败，3项恢复/边界组合通过。

## 最小修复

只修改DuckDBStore.cleanup截止条件的构造，不改schema、默认30天、设备覆盖/暂停语义、备份格式、API或配置值。普通Date可表示范围继续采用严格`ts < 截止点`，改用绑定参数；精确原生微秒边界仍保留。

超出Date范围时以BigInt计算截止微秒，使用原生epoch_us(TIMESTAMP)与绑定整数比较，避免双精度把前后1微秒折叠。负无穷仍过期，正无穷及NULL不会因本次计算误删。epoch_us(TIMESTAMP)的有限值是有符号64位整数，因此对于早于该类型最小值的截止点，仅把SQL比较操作数限制到该类型下界；没有任何有限时间戳会落在其下方。保存的秒数不修改、不新增业务上限，运行时Number.MAX_VALUE也保持原值。无穷保留时长仍非法，不把非法值静默改成永久。

普通清理条件仍按ts比较，不把所有日常清理改成epoch_us全列计算；不声称做过大数据性能测量或真实库升级。本修复不提供清理事务、跨库事务或已删样本恢复。

## 清理开关与恢复边界

| 设置/操作 | 实际行为 |
| --- | --- |
| retentionCheckMs=0 | 关闭周期定时器，仍有启动清理 |
| 全局retentionSeconds=0 | 只关闭全局过期规则，设备正数覆盖仍执行 |
| 设备dataRetainSeconds=0 | 该设备永久，排除全局规则 |
| 设备dataRetainSeconds=NULL | 跟随本次运行的全局值 |
| 设备暂停 | 不等于历史永久，自己的保留策略仍适用 |
| JSON配置恢复 | 追加暂停设备，不恢复样本或全局秒数 |
| 运行时全局设0后重启默认主入口 | 回到默认30天，不自动记住0 |
| 关闭后恢复物理副本 | 只恢复副本时点的数据；启动仍按当次策略清理 |

没有擅自增加一个与已有参数含义冲突的“全关闭”开关，也没有让JSON恢复自动暂停其他全局清理。若确实要保留隔离测试库的所有样本，须显式全局0，且每台设备为NULL或0；不能只把周期清理设0。对真实环境如何持久化全局策略、首次恢复是否需要额外清理确认，仍需另外设计，不能由本轮边界测试改变产品策略。
