# 主站保持寄存器来源绑定写入

同一数据目录只运行一个 ProbeStation 控制实例；其他普通 SQLite 配置写连接由代际触发器跟踪，但不支持多个控制实例并行控制同一通道。

恢复主站 TCP/RTU、FC03 点位定义上的 FC06/FC16 写入。此前只禁用弹窗和接口，没有交付可用的条件写入，不能满足设备控制需求。本次新增实际发送路径，不修改电机/压缩机固件，也不要求把读取分组改成“写模式”。

## 使用与更新

更新并重启 ProbeStation 后端，重新构建前端并刷新浏览器。无需额外 npm 依赖。首次打开新后端时，配置库迁移会在原有迁移事务内创建写入代际触发器及操作记录表；不修改设备/点位配置。迁移前按常规停止程序并备份数据目录。

在实时点表点击“写”或双击数值，输入原始值后直接点击“写入”或按 Enter。弹窗显示设备连接地址、从站、点位地址/类型；程序在一次用户操作内自动完成准备、来源核对和发送，不再要求额外准备或确认。写入方式可选 FC06 写单个、FC16 写多个，单字默认 FC06，多字类型只能 FC16。例如压缩机开关 `0x1000`，`0` 关、`1` 开。成功后保留弹窗，输入新值即可再次写入。当前读数缺失不作为禁止打开写入的条件；被多字覆盖和超出配置范围的点位不能直接写入。

配置变化会要求重新准备。每次确认仅执行服务端保存的计划，不能在执行请求中换目标或换值，不能自动降级到旧无条件写入接口。输入为原始值，factor/offset 不参与发送编码。所有 UI 设备/从站/点位来源条件都必须与后台一致。

## 接口及状态

所有新接口需要 `x-probestation-write: 1`，有 Origin 的浏览器请求必须同源。这是跨站请求防护，不是账号鉴权；软件仍面向本机/可信内网。

| 方法/路径 | 含义 |
|---|---|
| POST `/api/registers/:id/write/prepare` | `{version:1, value, source, method?: "single"\|"multiple"}`；不连接或写设备。source 使用 `registerWriteSource(device,group,register)` 的完整投影，返回服务端固定计划与操作 ID |
| POST `/api/register-writes/:id/execute` | 只接受 `{version:1}`。原子认领单次操作，再交给采集器及专用传输；重复请求只返回原状态 |
| GET `/api/register-writes/:id` | 查询原操作，不发送设备指令；过期/来源失效且未认领的 prepared 会持久化为 not-sent。刷新/重开弹窗通过 sessionStorage 中的 ID 恢复，不自动发送 |
| POST `/api/register-writes/:id/review-unknown` | `{confirmedOnSite:true}`；用户现场核实后记录原操作未知结果，解除该通道的未决阻止，不重发原计划 |
| POST `/api/register-writes/:id/cancel` | `{version:1}`；只将尚未认领的 prepared 计划改为 not-sent，迟到 execute 不会再发送；已接纳或已完成的操作不被取消 |

状态：prepared、sending、acknowledged、not-sent、unknown、reviewed-unknown。准备计划有效期为两分钟；后续配置变化、工作区/配置连接生命周期变化会使其失效。acknowledged 仅表示收到该连接上功能码、从站、地址及值/数量匹配的 Modbus 回执，不能据此声称电机已实际运转。

正常流程只有“关闭”和“写入”两个按钮。若响应丢失，只查询原操作；查询到 prepared 也不证明原执行请求不会迟到，因此不会自动新建计划。可取消尚未认领的计划后重新输入，取消与执行认领在同一 SQLite 互斥下决出先后；若已认领则保留 sending 状态。弹窗卸载或来源变化发生在自动准备阶段时，不会继续触发迟到的执行请求。

## 实际提交边界

1. SQLite 的设备/分组/点位 INSERT/UPDATE/DELETE 触发器更新随机 256 位代际。它与原配置写入同事务，回滚不发布代际，已提交 A→B→A 和其他正常 SQLite 写连接也会被识别。不依赖前端已收到配置广播。
2. 执行认领先持久化 sending；同一计划不可重放，同通道 sending/unknown 阻止新的准备和执行。进程在确认结果前结束时，下一生命周期将 sending 解释为 unknown。不能把超时、普通 HTTP 错误、重启当作未执行。
3. Poller 等待已有读取结束，阻止该通道新的调度及旧直接写/raw 获取，释放相同端点的轮询连接，避免只有一个 TCP 客户端名额的设备被旧轮询连接占用。RTU 通过共享队列串行，关闭轮询句柄，等待帧间隔，再打开带系统独占锁的专用句柄；TCP 同样使用每操作新连接，不复用 jsmodbus 的异步客户端/请求队列。操作结束后恢复常规调度。
4. 专用 native handle 打开后、不经任何 await 的最后提交点，由短 SQLite `BEGIN IMMEDIATE` 临界区核对计划、配置代际和生命周期，然后把固定字节交给固定 handle 的 `write`。该句柄不重连、不打开其他目标、不重试。锁只覆盖同步接纳，不跨连接或响应等待占用数据库。
5. 响应检查 TCP MBAP 的事务 ID/协议/长度/从站，RTU 检查 CRC/地址/长度，再核对 FC06/FC16 回显。异常、断开、提交后超时和响应不匹配均保守记录 unknown；结束后关闭操作句柄。诊断捕获使用既有通道缓存。

这是应用到固定原生句柄的来源绑定，不是物理设备身份认证，也不是数据库和硬件执行的分布式事务。原生 write 接纳后的配置编辑无法撤销已交底层的字节。RTU 没有事务 ID，匹配的回执不能证明物理因果或排除其他主站/延迟回声。支持正常数据库写者，不支持管理员删除触发器、直接修改代际/操作日志、在线替换数据库文件等绕过受控生命周期的行为。

## 范围与验证

当前开放 GUI/新 REST/MCP 主站 holding register、unit 1–247、明确 IP/端口的 TCP 或 8 位 RTU。旧无条件 REST、线圈写、本机从站内存修改和 OTA 的封闭策略不变。设备拒绝新连接时显示未发送，不更改目标或自动重试。

## MCP 写入与冲突修复

`write_register` 支持 `device_id/address/value`，可选 `slave_id/register_id` 精确选点；同址多来源不选第一项，返回 candidates。`method` 为 single（FC06）或 multiple（FC16，默认），多字类型必须 multiple。`value_mode` 默认 physical，按 factor/offset 反算；raw 直接编码原始值，支持字符串形式的 hex16、64 位整数。physical 只修正接近整数的浮点反算误差，不任意四舍五入非整数输入。

例如：`write_register {device_id: 3, slave_id: 1, register_id: 12, address: 4096, value: 1, value_mode: "raw", method: "single", request_id: "c731ec0e-796b-4ebf-a072-b262b69955dd"}`。示例 ID 须替换成实际设备/点位；每条新指令生成新 UUID。request_id 以小写保存；跨会话重用只查询原操作，不用新 value/method 重发。结果丢失时调用 `get_register_write_result {operation_id: 原request_id}`。未提供 request_id 时使用服务端生成的 ID；若整份响应丢失，调用方不知道该 ID，不能据此声称无重复风险。

MCP 与 GUI 复用配置库的准备/认领/最后提交校验、同一 Poller 来源绑定发送及持久回执。原有无条件 `poller.write` 不作回退，缺少新能力时明确拒绝。acknowledged 为协议确认；unknown/sending 不会被失效维护误标成 not-sent，也不自动重发。

修复的程序缺陷：来源比较不再依赖 JSON 字段顺序，但仍严格检查字段和值；prepared 因代际、生命周期或过期失效后转为 not-sent，重新打开窗口可输入并发送新指令；前端显示 Fastify 的具体 message，避免只见 Conflict；覆盖点检查按 group.id 取点，避免设备 ID 与组 ID 不同时漏检。新增 `test-register-write-recovery.ts` 使用实际 UI 请求/Fastify/SQLite/MCP SDK 与注入 wire 组合回归这些场景，不连接真实设备。
