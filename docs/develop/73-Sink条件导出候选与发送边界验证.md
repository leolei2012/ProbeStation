# Sink条件导出候选与发送边界验证

## 本轮决定

基于干净的`58a9ac22f6c9c7dab81011076c6ed41068b5e322`，沿实际Sink/导出GET验证候选方案。**未达到完整接入门槛，因此不启用生产能力**；不改变旧调用、签名、启动流程、数据库或前端，不扩展Workspace。新增代码仅为可执行的测试候选，未被主程序引用。

运行`npm run audit:sink-condition`（只接受`--memory`）。工具使用真实内存ConfigStore/DuckDB、真实Sink格式化、ExcelJS及共享Fastify导出路由inject；无listen、主程序、设备、Workspace、MCP或模型。输出`CONDITIONAL SINK CANDIDATE; REMAINING GAPS REPRODUCED; NOT A SAFETY PASS`，不加入安全测试白名单。退出0表示下面的证明与反例均符合预期，不表示产品已经安全。

## 候选契约与实现位置

候选全部定义在`scripts/audit-sink-condition.ts`，并非新的生产service或共享库：

1. 预览读取单事务配置副本，获取store句柄，将设备/ID选择/时间/时区、完整配置副本及store打开周期做SHA256条件摘要。绑定整个设备图，未选点的变化也保守失效；不自行丢掉quantity、零倍率或枚举等字段。
2. 候选执行时重新读取**一份**副本，在这份副本上比较预期条件；不匹配时不发时序SQL。将同一不可变副本注入实际Sink的只读配置提供者，不再让Sink重读真实config。时序读取映射到已有queryObjectForExportWithHandle，固定原连接代际。
3. 读取前、完整CSV/XLSX生成后检查原实例身份、句柄及当前内容条件。返回测试内的`{body, validate}`，让调用者能在自己的await之后再检查；不将它伪装成旧Sink的字符串/Buffer契约。

此条件约定的是“当前内容相等”，不是“中途从未编辑”。审计包含别名改走再改回（ABA），结果仍接受且文件用原副本；若产品要求任意中间编辑都撤销旧预览，必须另行设计覆盖所有写入方的单调revision，不能靠摘要承诺。该产品策略尚未在生产实现中选择。

## 已证明可工作的部分

- CSV/XLSX正常输出10，批次/来源与原格式保持；完全复用真实Sink，不重写格式化器。
- 预览后后台来源由1改2，执行在时序SQL之前拒绝；计数指时序SQL，不包括配置事务读取。
- Sink等待读取结果期间修改别名、factor=0、dtype或目标从站，配置scope均未改变，内容条件仍能发现并拒绝。读取屏障在真实SQL完成后、返回给Sink之前，证明的是异步读取等待窗口，未宣称在原生DuckDB内部执行指令间注入线程竞争。
- 真实XLSX字节已经生成，但writeBuffer的返回Promise被测试屏障延迟，期间编辑别名；释放后候选复核拒绝，不将生成成功等同于可交付。
- 预览后单独重开配置或时序库，原条件拒绝。数据库全部`:memory:`，相同ID和图由脚本重新创建，不恢复真实配置。

## 仍未闭合的具体缺口

### 一、路由交付边界

给**现有共享真实GET路由**注入候选包装：候选完成生成及内部复核后，在旧字符串返回到路由前改别名。路由仍HTTP200并挂附件，条件此时已不匹配。反例中的编辑是测试明确插入的步骤，证明仅Sink内部检查不足以承诺“交给路由发送时条件仍满足”；不是声称旧API本来就承诺版本条件。

测试内另建`/audit/checked`，await候选后先validate再设置附件头，同样编辑得到409且无Content-Disposition，证明能关闭这个特定窗口。该路由只在内存测试存在，没有注册到产品。将来还需明确最终核对发生在同步交给框架的边界，不能承诺网络最后一字节发出后配置仍未变，也不应跨整个下载持有配置写锁。

### 二、重新预览不能建立初始配对

保持内存config原scope，独立重开内存store并写入200：旧条件会拒绝，但重新preview后，新条件可以通过、文件输出200。它只知道这两个实例当前状态相等，不知道二者是否由同一次单目录装配拥有或原本属于同一逻辑会话。这个反例是受控内存生命周期组合，不表示当前CLI有公开重开接口。

因此不能在首次导出/每次预览时“都ready就配对”。72号要求的单目录启动拥有关系仍未建立。本轮不为补缺口而恢复Workspace，也不添加另一个未接入的全局配对service。

### 三、兼容且可检验的调用协议

候选只在脚本里，尚无生产preview/checked请求、能力版本、成功回执或客户端核对。把expected塞进旧GET、或成功时无条件回退旧方法，都会重复旧后端忽略条件却返回附件的风险；本轮不这样接入。旧Sink字符串/Buffer调用及外部旧GET保持原样，也就保留旧限制。

## 最小后续切分

先在**实际单目录装配点**制定并证明初始化成功/失败和原实例的拥有关系；不要从请求时的可用性反推。之后才把候选收敛为实际Sink内的条件collect及生成后验证上下文，保证检查和解码使用同一图；不另读一份配置再调用旧export。

随后新增可选、版本明确的只读checked入口，消费该上下文，在await之后且挂附件前核对；失败只有JSON且不自动重试，旧入口继续兼容。客户端必须核对能力和实际revision回执，前端打开时已见定义也需与preview一致，不能悄悄采纳后台新来源。再补完整CSV/XLSX/来源与限额边界、初始化失败、provider替换、预览/等待/生成/路由各阶段、旧客户端/旧后端的组合测试，证明后才启用。
