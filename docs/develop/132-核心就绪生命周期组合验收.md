| 场景 | 结果 |
| --- | --- |
| 配置已隔离，真实DuckDB INSERT失败且ROLLBACK成功 | `/ready/core`503，同时公开quarantined与flush-failed；不输出异常详情 |
| 存储仍失败，配置显式重开失败 | 组合仍503，不清除配置隔离 |
| 存储仍失败，配置显式重开成功 | 配置ready、存储failed，组合仍503 |
| 显式重试存储flush成功 | 缓冲清空，两项ready后组合才200；没有自动重试 |
| 存储reopen的flush被受控门挂起 | storage=switching，组合503 |
| 上述switching期间配置重开失败，再成功 | 分别quarantined/ready，存储仍switching时均503；释放门并完成实际reopen后200 |
| 配置开始终止close，消费者清理门尚未释放 | SQLite物理连接仍打开，但configuration=unavailable，组合503；重复close共享任务 |
| 此时存储从真实flush失败中恢复 | 存储ready仍不能覆盖配置的关闭状态；旧`/ready`仍按其范围返回200 |
| close期间或完成后尝试配置reopen | 终止状态拒绝重开，组合仍503；释放清理门后物理连接关闭 |
| 实际store插件卸载 | 依赖API服务撤销，保留的旧Fastify实例拒绝新`/ready`与`/ready/core`请求 |
| 重新装配store插件 | 产生不同API实例；新实例两依赖ready才200，旧实例保持关闭 |
| 直接卸载新API、重复卸载 | 服务撤销，保留引用拒绝新请求，不因数据库仍可用而复活 |

关闭等待组合使用真实ConfigStore/DuckDBStore及独立Fastify注册，后者特意未登记为配置消费者，以便在物理连接仍打开时观测配置close标志。它不是“完整生产API在配置close期间仍接收请求”的证明。真实插件另用store卸载/替换及直接API卸载测试，关闭后应拒绝新请求，不要求仍返回JSON503；原preHandler门控覆盖已进入处理器前等待的请求。

所有数据库都是本轮新建合成SQLite或内存DuckDB。存储故障注入只拦截本实例INSERT；门控只作用于本测试实例。失败消息使用PRIVATE哨兵，响应不含该字符串或临时配置路径。listen/connect/fetch仍被阻断，末尾检查拒绝计数与unhandledRejection均为空；真实插件不注册CLI监听器或任何驱动。

## 响应交付时间边界

额外一组通过Fastify的onSend门延迟一个已经生成的200：

1. 配置ready时，处理器完成只读状态采集并生成200。
2. 响应交付被测试门暂缓；此时关闭配置连接。
3. 新请求503且configuration=unavailable。
4. 释放旧响应门，原响应仍携带采集时的ready和200，Cache-Control:no-store。

这是可复现的观测时间限制，不将其误称为已解决的交付时强一致性。原处理器没有在关闭后重新采样出ready；已有“preHandler等待→关闭开始→处理器执行”的场景仍返回503。配置reopen本身为同步操作，普通同进程请求不能穿插进其同步调用中间；异步存储切换则由switching明确阻止就绪。

任何HTTP探针都可能在处理器采集后、网络交付或下一请求前变为过时；新增onSend复核仍无法覆盖网络或代理排队，也不能授予可用性租约。本轮不靠重排响应钩子承诺此性质，不自动复核SQL或重开连接。监控应采用原版本/scope/状态校验和新鲜轮询，不能将一次200当作业务写入承诺。No-store也不是消除传输延迟的保证。
