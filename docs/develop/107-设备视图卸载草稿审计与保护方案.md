## 为什么不直接在cleanup里确认

React已经切换分支/key才执行卸载清理。cleanup无法撤销父组件的状态变化，也无法保证重建时找回旧hooks；在那里window.confirm或发送保存请求既无法保护此草稿，又可能阻断正常关闭/成功保存或重复写入。单加beforeunload也覆盖不了同页设备切换，且浏览器可限制提示，不是持久保存。全局拦截每次点击则会干扰相同设备/相同视图和本来不卸载该编辑器的操作。

仅给旧组件加“保存成功”提示、将当前配置重新加载当草稿恢复、或在后台设备消失后继续假装设备存在，都不安全。本轮没有实施这些假保护，也没有改真实配置或保留过时设备状态来阻止刷新。

## 最小分步建议及验收契约

第一步建议只保护应用可控的卸载意图：编辑器向App持有的临时注册器提供最新dirty/busy和所属范围（设备编辑器属于设备视图、点位编辑器属于实时表格），不注册密码/模型信息，不存草稿值，也不改变保存API。

| 情形 | 建议行为 |
| --- | --- |
| 无草稿或草稿干净 | 原导航直接通过，不弹确认 |
| 同一设备/同一视图且编辑器不会卸载 | 直接通过，保持原一次性跳转语义 |
| 确会卸载且有脏草稿 | 在任何selected/view/target/token变化前询问是否放弃；取消则所有导航副作用均0，草稿保持 |
| 明确放弃 | 原导航只执行一次，不自动保存/撤销或重试配置写入 |
| 保存结果尚未明确/busy | 不通过导航强制中断或重放保存，给等待/核对提示；成功回调关闭不误报草稿丢失 |
| 显式关闭、成功保存或组件已经移除 | 及时注销，后续干净导航不被过期注册阻断 |

必须覆盖设备按钮、助手/提醒引用、全局数据库切换和会卸载LiveTable的标签跳转；只把一个按钮包起来不足以称为完成。旧回调的正常无草稿结果、排序/搜索、同设备点击、显式重复引用和取消导航的副作用需做真实回调组合验证。此方案可独立交付，但仍不能声称覆盖后台强制移除。

第二步处理非用户可控卸载：把活跃编辑器或完整原始草稿的所有权提升到会继续存在的App层，在设备从配置列表消失时仍能只读查看/记录草稿。必须同时保留原打开条件与原始文本、枚举未提交状态，明确“仅当前标签页内存、未写配置库、刷新仍可能丢失”；不默认为持久保存，不把旧数据自动套到同ID新设备或新来源上，不阻止新配置发布或采集状态更新。继续编辑/保存必须沿用既有冲突条件，设备不存在则不可保存；浏览器刷新/关闭另作独立可选提醒，而非承诺可恢复。

这涉及App与两个编辑器的生命周期和成功保存顺序，不能靠在子组件补一条cleanup完成。本轮按任务先完成可复现证据和最小安全评估，没有静默引入未接入注册器、全局模态或新的草稿存储机制。推荐下一轮先做第一步，再单独验收第二步；当前缺口明确保持未解决。
