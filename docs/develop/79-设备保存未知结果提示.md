# 设备保存未知结果提示

## 证据与范围

基于干净的`84d979eeb7f4c0d298cc658c07ed993fc37c3ca8`检查配置写入后的响应丢失。实际App的editDevice调用saveGuardedDeviceSettings，DeviceModal捕获异常后保留草稿，但旧helper直接透传put错误。内存SQLite和实际registerDeviceSettings路由先成功保存，再由模拟传输抛TypeError('Failed to fetch')：旧回归断言失败，显示原网络错误，没有说明设备配置可能已经保存。

这轮只修复设备有条件编辑的错误提示，不改变设备新建、分组、点位、告警或旧REST/MCP语义，不加入额外读写请求。

## 最小处理

- 保持parseDeviceEditRequest在请求之前，本地无效草稿原样拒绝，不包装成已发送或结果未知。
- 只对单次put调用捕获异常。沿用现有分组helper的HTTP错误约定：明确的400/403/404/409/413/415保留原Error和原因；网络异常、响应解析失败、5xx及其余无法分类的异常统一提示“保存结果待核实，请核对设备配置，勿自动重复保存”。
- 原成功响应校验、warnings返回和冻结保持不变。没有自动重试、无条件接口回退、自动回滚或读回确认。当前值等于草稿不足以证明这次写入及运行时应用成功，因此不能据此自动关闭窗口、宣称成功或重建打开时基线。
- 实际DeviceModal沿用现有错误区域及草稿保护，不改结构、保存载荷或父级成功关闭逻辑。结果未知时保存按钮仍遵循既有手动操作，本轮没有实现幂等或阻止用户忽略提示再次保存。

HTTP分类依赖现有App请求函数的`HTTP <status>`错误格式，不新增API字段或服务端行为。未知结果是保守提示，既不保证已经保存，也不保证没有保存。明确错误响应只代表该请求的拒绝，不推断此前丢失响应的请求结果。

## 回归与边界

扩展已有两个安全白名单测试，不增加主应用启动、网络监听或设备动作：

- test-device-edit-conflict使用真实内存ConfigStore和实际设备设置路由，先提交再丢响应，核对只一次请求、一次配置通知及原两项mock运行钩子。人工使用旧快照重试返回409，不再写库或运行钩子；网络/解析/5xx/非Error错误仍未知，已知拒绝保留同一Error，本地校验零请求。
- test-device-draft-close执行实际组件事件→实际helper→实际路由→内存库，模拟成功后丢响应。断言草稿保留、未知提示显示、没有成功回调或关闭、重复提交在忙时被锁住；等待/重绘不重试，人工再次提交仍409，明确放弃草稿不触发撤销或重试。
- 原正常保存、warning校验、并发/回滚及关闭草稿回归继续保留。hook事件驱动及SSR不能替代真实浏览器React DOM、焦点、网络代理或布局验收。
