# 设备保存写前隔离与结果未知区分

基线`a94a2bfc24132f035e6d1cb3006d9db9e2489240`，初始工作区干净。本轮限定条件设备编辑`PUT /api/monitor_objects/:id/settings`及其前端保存路径，不改变配置事务、恢复方法、设备采集、旧无条件PUT或其他写接口。

## 证据与边界

真实内存ConfigStore加Fastify.inject故障注入，分别让COMMIT执行前抛错、COMMIT实际完成后抛错，两者ROLLBACK都抛错：原请求均500且结果未知，配置连接进入隔离。原方法没有完成正常返回、配置通知或运行时重连；本地读出的相同名称可能处于未提交事务或已经提交，不足以确认原请求结局。

随后发起独立设备保存，原实现因隔离在首个数据库入口拒绝，却又统一转换成500“结果待核实”。基线两个回归均在实际编辑器提示分类处失败：后续明确没有开始的请求也显示与原事务错误相同的未知信息。已有错误路径会保留编辑草稿，本轮没有将此既存行为称为新功能。

修复不根据异常名、503状态本身或先前事务错误推断本次未执行。路由在调用updateObjectSettings之前仅读取可选配置状态：只有version=1、phase=quarantined、failure=connection-quarantined组合才立即返回；不调用保存方法，不做SQL，不运行重连/从站同步。

## 新拒绝响应与兼容

写前已确认隔离时返回HTTP503：

```json
{
  "error": "配置连接已隔离，本次保存未执行。请管理员核查并恢复，勿重复保存；之前请求结果仍须单独核实。",
  "version": 1,
  "code": "CONFIG_WRITE_NOT_STARTED",
  "outcome": "not-applied"
}
```

这只描述该请求没有调用保存方法；不证明设备存在或编辑快照有效，不清除隔离，不证明更早的请求是否提交，也不是幂等凭据、恢复授权或未来写入许可。已隔离状态优先于body的业务校验；URL编号格式校验仍先返回原400。

方法调用后所有既有catch分类保持：已知400/404/409原样拒绝；提交、回滚或其他未知异常仍500且无此标记；提交后的通知/运行时同步失败仍按原成功+warnings处理。没有状态方法的旧provider仍执行原路径，未知异常保持500。旧无条件REST未改。

App.request保留原HTTP错误文本，并只在HTTP503与上述version/code/outcome同时匹配时附加请求错误元数据。设备保存helper只接受完整元数据为“本次保存未执行”，说明草稿留在当前窗口、请管理员核查恢复、先前结果单独核实；普通503、字段缺失/不匹配、500/502/504即使携带同名字段、以及网络/返回丢失均保持结果待核实。没有增加取消、超时重放、回退接口、连接重开或任何写入重试。

旧前端会将新503视作原来的未知错误，仍保守提示且不自动重试；新前端遇旧服务端500/普通503也保持未知。该兼容结论基于原helper的503默认分支、原回归和新边界测试；未声称已用实际旧浏览器版本做端到端验收。

## 回归

新增device-write-quarantine套件，白名单136套，services严格检查纳入新脚本；4组：

1. COMMIT执行前错误+回滚失败：原保存未知，隔离后的下一次保存明确未开始。真实路由→实际App请求适配器→设备保存helper→实际DeviceModal模拟hooks完整执行。
2. COMMIT完成后确认错误+回滚失败：相同响应下原行确已提交，原请求仍未知；新请求仍明确写前拒绝，不替原请求断言。两组均用prepare/exec哨兵证明拒绝不执行SQL、通知和运行时hook计数不变；编辑输入保留、没有成功关闭、关闭确认可取消继续编辑、每次仅一个请求。
3. 版本/代码/结果缺失或错误、普通503、500/502/504及响应丢失均未知，单次调用不重试，模拟PRIVATE错误详情不进入已处理的保存提示。
4. 不带状态方法的旧provider保留原500未知行为，不执行运行时hook、不泄漏原异常。

所有数据只在新建内存SQLite；网络请求替换为Fastify.inject，不监听端口。设备地址和串口字段都是合成元数据，运行时hook仅计数，未创建驱动或调用模型。没有重开连接或读取真实库。
