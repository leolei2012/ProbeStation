# 新增分组启用状态保真

## 证据与范围

基于干净的`ab45f0a6a7730bc3d3e0ca7da45c5f283ba27c1f`，检查相邻分组配置流程发现一项实际缺陷：GroupModal新增表单把“启用”复选框转为数字isActive=0/1，但POST `/api/monitor_objects/:id/groups`不传此字段，ConfigStore.createGroup的INSERT也没有该列，只能取数据库默认1。因此取消启用仍得到启用组，和用户操作不一致。

先新增回归并执行实际表单事件、实际POST和真实`:memory:`配置库：表单取消勾选后请求体确为0，HTTP200响应却isActive=1，断言失败。不是用手写等价handler替代，也未调用在用服务或操作设备。

本轮仅修创建时的启用状态，已有点位/设备草稿保护和编辑并发保护不重复实现；不扩展导出/Workspace设施。

## 最小修复与兼容

- REST将b.isActive明确放进createGroup的具名options。ConfigStore选择省略为1，显式只允许数字0/1，其他值在SQL和通知前抛400；不将null/布尔/字符串静默变成启用。
- INSERT直接绑定is_active，不采用先按默认启用创建、再update暂停的做法。首次group通知和随后register通知都能看到最终0，现有主站active-group筛选会排除该组，不制造短暂启用阶段。这里没有保证设备其他分组不采集、设备连接一定关闭或模拟从站所有行为。
- 旧7参数createGroup和旧请求不传isActive时仍默认1，选中启用也仍为1。mode/Slave ID位置、寄存器按数量生成、FC和默认int16保持原样，不改变现有组/设备。
- 旧config README误写第8个pollIntervalMs，而旧实际方法只有7参数，多余数字被忽略。新增采用`options?: {isActive?: number}`，避免把旧数字0误解释为停用；回归证明旧动态额外数字仍不会成为开关。文档已修正，不承诺该旧间隔曾生效。
- 没有schema/持久身份/真实数据迁移；新状态写在已存在的is_active列，绑定参数，不拼接SQL。

这个改动不把整个“创建组＋循环创建默认点位”升级为原子事务，也未统一校验旧接口全部其他字段。通知失败、点位创建失败及旧无条件接口其他限制仍按原行为；不宣称本轮解决了它们。
