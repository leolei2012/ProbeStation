# 配置与采样存储组合就绪探针

基线 `a6147445e2b40ffa0affb2bd2ce115345401f926`，初始工作区干净。只使用独立候选、新建合成SQLite、内存DuckDB、实际Cordis/API装配与注入请求；没有启动CLI主入口、监听网络、连接驱动或接触真实数据。

## 现象与兼容决策

真实装配中，故障注入使配置连接隔离后，GET /api/monitor_objects返回503，GET /ready仍返回200及scope=sample-storage，采样存储自身状态确实就绪。这符合既有契约，不能称为原接口错误地报告其已检查依赖；风险在于将它误当作配置或整应用可用性的放行条件。

不改变既有GET /ready的状态码、完整响应体、查询参数口径与两参数registerReadiness调用方式，也不改变/health存活响应。新增独立GET /ready/core，显式要求配置连接及采样存储的状态均可核实为ready；不能悄悄升级旧探针而让旧监控的scope/字段解析失效。

| 接口 | 检查范围 | 就绪条件 |
| --- | --- | --- |
| /health | HTTP存活 | 原响应和200契约保持，不作为依赖就绪证明 |
| /ready | 全服务采样存储状态 | 原有已核实phase=ready、failure=null才200，其余503 |
| /ready/core | 配置连接本地生命周期/已知隔离状态 + 全服务采样存储状态 | 两项均核实ready且API未进入关闭才200，其余503 |

两个就绪端点均Cache-Control:no-store；object_id、storage_only等查询参数不能将组合端点降为单设备或只检查存储。没有自动改变任何部署、负载均衡或外部监控配置。

## 新接口与只读状态

```json
{
  "version": 1,
  "status": "ready",
  "scope": "configuration-and-sample-storage",
  "storage": { "phase": "ready", "failure": null },
  "configuration": { "phase": "ready", "failure": null }
}
```

非就绪保留同样结构、status为not-ready。storage沿用原严格解析和脱敏状态；configuration只公开以下已知本地状态，不公开路径、连接参数、异常cause或具体数据库错误：

- ready/null：未开始终止close、无已知隔离且本实例原生连接isOpen；不是执行SQL健康检查。
- quarantined/connection-quarantined：已隔离，包括恢复打开失败后仍未解禁；原生fixture手工ROLLBACK不能解除。
- unavailable/lifecycle-unavailable：终止close已开始（含完成），或连接已关闭。
- unavailable/unavailable：未提供配置状态服务或当前API已开始关闭；不能把未检查当作ready。
- unknown/status-unverified：提供者抛错、版本/字段组合不合法、返回异步Promise或未知状态；拒绝就绪。异步拒绝被收集，不泄漏为unhandledRejection。

ConfigStore新增getConfigurationReadinessStatus，仅读取内存标志及原生isOpen属性，返回冻结的版本化状态，不经过受阻的数据库读入口。没有prepare/exec/SELECT、写入、flush、cleanup、reopen、retry或通知。原隔离/错误/恢复行为未改。

registerReadiness的第三个配置提供者为可选参数：旧两参数调用继续获得原/ready行为，但新/core因配置未检查而503。生产API显式传入当前配置状态方法；旧/不兼容配置服务没有该方法时，不用SQL探测或默认正常来兜底。

## 监控迁移与范围

只关注采样存储的旧监控可继续/ready。需要同时拦截配置隔离时，显式改用/ready/core，并验证HTTP 200、version=1、scope=configuration-and-sample-storage、status=ready及两项phase=ready/failure=null；404、503、连接失败、未知/非JSON响应都不是就绪。不能回退到旧/ready或/health判成功；基线旧版本没有新路径，隔离测试返回404。

“core”不表示全依赖：没有检查设备在线、串口、PLC、从站监听、采集器调度、模型服务、告警日志、磁盘未来可写性、样本完整性、队列全部落盘或两库身份配对。健康缓冲/进行中的flush不因队列非空被判失败，沿用原存储契约。探针是状态观测，不是事务提交回执、跨依赖锁或未来请求的可用性租约。

## 隔离回归

新增test-core-readiness，共7组：

1. 实际ConfigStore在ready、隔离、原生手工清理、失败重开、成功恢复、终止关闭中的状态；prepare/exec故障哨兵证明状态读取不做SQL，通知次数不变。
2. 旧响应完整deepEqual、旧/ready不调用配置提供者，新/core严格限定scope、no-store和两个依赖。
3. 缺配置提供者时旧接口200、新接口503，防止把未检查当作成功。
4. 畸形/未来版本/不匹配状态、同步抛错、异步拒绝和未决Promise全部非就绪；私有附加字段和错误细节不进入响应。
5. 配置和存储独立失败/恢复，任意一个失败均阻止组合就绪；另一项状态仍分别公开。
6. 已进入请求在preHandler等待时开始关闭，新/core503且不调用状态提供者，完成后不再接收请求。
7. 真实Cordis配置/存储/API插件，无网络监听：配置隔离时旧探针200、配置GET503、新探针503；禁止SQL/flush/cleanup/reopen/queryObject的哨兵证明探针不触发恢复。手工清理及失败重开仍503，明确恢复后200；/health保持，API关闭后请求拒绝。

基线7组新增契约断言失败，原因包括新方法/路由尚不存在；其中实际装配明确记录原200与配置503的范围差异，不将7条新增功能断言称作7个既有产品缺陷。首次本地runner命名冲突导致target-1执行了旧readiness套件，已纠正，该日志不作为新功能验证。最终目标日志为core-readiness-target-final；严格检查修正了测试初始化等待的私有字段适配及必需服务断言，没有放宽编译选项。

旧readiness套件的真实初始化、flush故障/恢复、reopen、状态错误、关闭及Cordis依赖替换回归保持；另重跑api-lifecycle和14项config-quarantine。所有数据库及API数据目录均为本次新建/内存；清理前核验绝对父目录、前缀与非链接类型。net listen/connect/fetch被禁止，未出现真实I/O或未处理拒绝。
