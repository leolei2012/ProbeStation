## 范围与已复现问题

基于`7f38d64641e53ca4e7c18569560ca709ea6a1868`，保持CLI主入口、信号行为、采集/设备连接、数据保留规则及DuckDB迁移代码不变。所有数据库均由测试在新建临时目录生成；没有读取用户库、启动主应用、连接设备、调用模型或操作在用服务。

历史配置schema按Git源码核对：`3d8cdbe`初版只有设备、分组和点位基础表，没有分组slave_id；`9827971`引入分组slave_id（默认1）及分组poll_interval_ms。没有拿真实库作fixture。

修复前运行新回归：8项失败、2项通过，准确复现：

- 初版库打开后listGroups报`no such column: slave_id`。CREATE TABLE IF NOT EXISTS不会补已有表的列，现有迁移遗漏该列。
- 所有ALTER异常都被当作“列已存在/不存在”吞掉；注入中途加列或删列错误后构造仍成功，已完成的DDL逐条提交，没有整体回滚。
- 当前库重复启动仍逐条尝试必然失败的ALTER，不根据实际schema跳过。

## 最小修复与兼容

ConfigStore.open在单个`BEGIN IMMEDIATE`事务内执行建表、补列及既有废弃列删除，最后COMMIT。BEGIN失败不ROLLBACK；执行失败尝试ROLLBACK，保留原错误。回滚再失败以AggregateError保留两条错误；外层继续关闭SQLite句柄，关闭错误仍按原清理机制保留。不新增自动重试、数据重写或启动健康策略。

按PRAGMA table_info判断哪些列存在，存在则跳过，不再捕获并忽略任意DDL异常。只补原有升级字段和遗漏的分组slave_id，沿用历史配置默认1；这不是对历史样本从站来源的推断。已有非默认值、点位quantity（不按dtype重算）、零倍率等保持不变。不尝试修复未知表类型/自定义schema；未知索引若阻碍旧列删除，明确失败并回滚，不擅自删除索引。未增加schema版本表或破坏旧API。

DuckDB已有事务迁移继续保留：register_id改为address，缺area按原holding-register默认，batch_id/slave_id均可空且无默认；旧历史身份仍NULL。有身份的新样本关闭重开后保留身份。多字旧值可兼容显示，但未验证，不变成自动判断依据。

## 启动清理及回滚含义

当前主入口未显式设置retentionSeconds，Store配置默认2592000秒（30天）。成功初始化后即调cleanup；`retentionCheckMs=0`只停周期定时器，启动清理仍执行。设备非NULL覆盖全局，0为永久；retentionSeconds=0仅停全局清理，仍须注意设备正数覆盖。测试中需要全保留时同时避免设备正数覆盖。这是既有行为，本轮未改变策略。

因此生产首次成功升级后，符合保留策略的旧数据仍可能被删除；schema迁移事务不涵盖后续清理，也不涵盖另一库。初始化失败则本次历史库启动清理不运行；这不代表主程序其他插件会自动整体回滚。

“回滚”有两种含义，不能混淆：失败且ROLLBACK成功时撤销本次配置DDL；版本降级则需要另外规划。合成验证已证实旧代码依赖的分组poll_interval_ms已删除、最早历史register_id已改名，直接换旧二进制会查询失败。仅使用address且忽略新增列的旧SELECT可继续读取，不代表所有旧程序可运行；旧INSERT兼容矩阵不在本轮覆盖。

本轮只验证**所有连接关闭后**复制合成升级前两文件副本、升级后关闭再恢复副本。未实现在线备份、跨库原子快照或自动降级；恢复旧副本会丢失副本之后的新配置和采样，不能用于运行中替换。清理已经删除的行也不能靠切回旧代码恢复。
