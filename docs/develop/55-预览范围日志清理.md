## 需求与范围

原按钮立即POST无条件/api/logs/clear，语义是删除当时全部日志，点击前后新记录也被删除；无预览、确认或结果不明处理。内存复现：记录旧ID后插入新日志，再调用原clearLogs，新日志亦为0条；“清理已审阅范围应保留之后新日志”的断言先失败。这不是改写旧接口原定义，新UI明确采用更窄的“预览截止范围”语义，旧REST/clearLogs保留兼容。

## 存储与接口

previewLogCleanup只读取logs表已识别的id INTEGER PRIMARY KEY AUTOINCREMENT契约及COUNT/MAX，返回version=1、throughId、count和revision；无记录时0/0。revision用每个ConfigStore私有随机范围及数字条件生成不透明摘要，不返回路径或日志内容。连接重建/重开数据库使旧条件失效；这不是鉴权、持久修订或内容审计。

cleanupReviewedLogs仅接受原expected条件，来源/格式不符拒绝。BEGIN IMMEDIATE内再次核对递增ID契约，统计id<=throughId的现存数量，再参数化DELETE同一范围并读回范围为空和剩余总数后COMMIT。只针对已确认ID前缀，正常新增ID更高而被保留；相同范围重复请求不会扩展到后续ID。原范围被保留清理/其他删除先行移除时，结果以deleted及alreadyRemoved分别报告；remaining为事务内读回的总剩余数，不是响应后永远不变的数。

现存数量大于原count或契约未知会拒绝。没有迁移旧表，未识别的DDL形式（即便可能语义等价）保守阻止新入口，不能自动回退无条件清空。SQLite回滚错误明确抛出并作废旧范围，阻止该实例再发清理预览/执行，直到人工排查后显式成功重开；不自动重开或宣称所有配置操作已有全局故障封锁。

GET /api/logs/cleanup-preview不缓存，错误503固定文本。POST /api/logs/cleanup body={expected}，限制16KiB、严格字段/正安全计数，要求x-probestation-config:1，Origin若存在需与Host匹配。条件不符409、非法400、头/来源403，其他错误500固定文本表示结果待核实，不泄露SQL/错误原文。成功返回ok/throughId/revision/deleted/alreadyRemoved/remaining；客户端核对原条件、计数关系与完整回执。

## 用户流程

设置→数据→“预览日志清理”只发GET。对话框显示全服务数量、截止ID和本页UTC接收时间，说明包括近期200条查看器外的旧记录、删除不可撤销、不影响样本/设备配置或文件、预览后新增保留。空范围不能确认。仅用户再次点击“确认清理预览范围”才POST冻结条件。

本页内存LogCleanupFlow同步消费条件，阻止重复确认；写请求不设AbortSignal或业务超时、不自动重试，10秒仅显示慢请求提示。关闭/重开窗口仍能看到同一进行中/已完成/结果不明状态，不能误以为关闭取消写。服务端确认拒绝与未知结果分开：500/断线/异常成功回执为uncertain，直接重复确认无效，必须明确新预览并再确认；不通过近期日志是否为空来自动推定上次成功。读取预览10秒超时/可取消，迟到响应不发布。新预览的“未发起清理”只描述该次读取，不否认更早未知操作可能已执行。

正式对话框Portal到body，开启聚焦关闭按钮、Tab循环/Escape关闭并恢复原焦点；均type=button，防表单误提交。结果到达后设置中已展开日志查看器只读刷新；预览/筛选不会删除日志。未提供旧方式强制清空按钮。

## 剩余限制

旧无条件REST及任何外部直接SQL删除仍可能清空全部，不在新保护范围。新条件依赖应用正常维护的AUTOINCREMENT/追加与删除语义，不验证每条消息未被外部改写，也不防数据库DDL/序列被外部任意篡改；有疑问应停止操作并人工核对。不是完整鉴权、跨实例共享事务令牌或持久审计；多后端连接/重启可能拒绝旧条件，需要新预览。记录数与ID不包含完整日志内容。

本页状态不持久化，浏览器刷新丢失操作视图，不证明旧请求未执行；目标仍是原固定前缀。未来日志可继续增加，成功不表示持续零日志。没有更改采样历史、告警阈值/联锁、日志保留策略、全局配置事务故障策略或模型权限。本轮未执行部署/重启，未核实运行页面是否已使用本地构建产物。
