# 外层事务通知时机与订阅者审计

基线 `38ac41e8667075f62030861813b9e2b2b6f878f0`，初始工作区干净。只用独立候选目录、17 个新建临时 SQLite fixture、既有依赖、实际 Cordis 同步事件、未启动采集的实际 poller 插件和实际 Recorder。没有读取真实库、创建真实驱动、启动轮询、监听网络或覆盖在用构建。

## 结论与适用范围

`config/changed` 是同步配置失效通知，不能当作最终提交回执。对绕过 ConfigStore 私有连接边界的外层事务，旧可组合方法的 SQL 保存点结束不等于外层提交：通知已经发出，调用者仍可回滚整个事务或自己的保存点。直接延后通知缺少可靠的事务拥有者/完成信号，本轮不改生产通知顺序、事务、协议、错误分类或采集行为。

这不是已证实的普通 REST 删除必现问题。源码检索未发现 apps/packages 中其他模块绕过该私有连接开启外层事务；本轮外层控制仅由审计的窄测试适配器模拟。ConfigStore 自管的创建、编辑、点表/备份事务使用其现有提交/通知安排；不是所有方法都支持嵌套。外部插件或下游 JS 绕过 TypeScript private 的使用情况无法据此排除，不能声称所有外部集成都安全。

## 已验证的订阅者

| 路径 | 实际行为与回滚影响 |
| --- | --- |
| ConfigStore.apply → Cordis.emit | 当前已安装 Cordis 的 emit 同步依次调用订阅者；中途同步抛错会停止后续订阅者。ConfigStore 仅在调用回调前无事务时分类为“已提交、通知失败”；外层事务内仍抛原错误，不替调用者提交或回滚。 |
| poller 的 config/changed → refreshSchedule | 立即读取同一 ConfigStore 连接，更新设备/组缓存，并可能释放已删除/停用来源的驱动。回滚不会再触发 refreshSchedule，因此缓存可持续保留事务中的状态，直到另一次有效刷新；已释放连接不会因 SQL 回滚自动恢复。 |
| Recorder 的 object 事件 → inspectSources | 读取同一配置并核对来源。来源改变/删除可结束录制、撤销间隔归还资格并保留样本及核对提示。SQL 回滚不会重开会话，也不能撤销已写入的内存核对记录。来源/lease 的进程内身份本来就保守地对尝试修改失效；不能据此推导“只要延迟通知就能继续旧录制”。 |
| API 的 config/changed 中继 | 立即广播原 `{type,scope,id}`。审计执行从生产源码提取的原注册回调，收件者仅为内存数组；已广播消息无法被原数据库回滚撤回。没有真实 WebSocket/代理验收。 |
| 前端接收 config/changed | 实际源码会调用 refreshDevices/refreshRegisters。若 GET 在回滚前由同一配置连接处理，可能获取待提交状态；若 GET 在同步回滚后才被处理，则可能仅产生多余刷新。本轮未运行真实浏览器/HTTP，因此不把所有界面请求都说成必然读到错误状态。 |

同步事务块中的通知和采集缓存更新确实先于调用方后续 ROLLBACK；JS 事件循环上的 HTTP 请求不一定有机会插入该同步块。审计明确区分这两种时序，不将两连接重叠读取冒充多进程或浏览器并发验收。

## 17 项合成证据

1. 设备/组/点删除 × 外层 COMMIT/ROLLBACK，共 6 项：通知时 writer 为待提交删除图，另一只读连接仍读完整旧图；方法不代为提交外层事务。COMMIT 后另一连接才读到删除；ROLLBACK 后两连接均恢复原图，但通知和内存中继各仍只有原来一次，没有撤回或完成事件。无关设备保持原样。
2. 真实 Cordis 订阅者中途抛错 × 调用者提交/回滚，共 2 项：前面的订阅者/中继已执行，后面的订阅者未执行；删除方法抛同一原错误，事务仍待调用者决定。错误本身不能说明删除最终是否提交。
3. 调用者保存点回滚后提交，共 1 项：删点通知已经发出，但 ROLLBACK TO caller_inner 撤销删除，最后外层 COMMIT 的数据仍为原图。“最终发生过 COMMIT”也不足以证明这个事件代表的动作保留。
4. 微任务延迟，共 2 项：事务跨一次事件循环仍打开时，延迟读取仍是未提交时刻；若先同步回滚再执行微任务，isTransaction 虽为 false，却是回滚后状态。延迟或只检查该布尔值都不能识别提交事实。
5. 实际 poller 插件的来源编辑/删除，各 1 项：始终不 startAll，注入服务禁止创建驱动；编辑时缓存改为待提交地址，删除时缓存消失并释放一个模拟驱动。回滚恢复数据库而不恢复缓存；测试显式发出另一次合法同值元数据更新后缓存才刷新。该显式恢复不是生产自动重试，也不能撤回连接释放。
6. 实际 Recorder 的来源编辑/删除，各 1 项：录制原有 1 个合成样本，通知后以 source-changed 结束并保留间隔。回滚后配置和日志图恢复，但会话仍结束，后续合成帧不再追加，当前 100ms 间隔不被不安全地写回旧值。未自动恢复、重录或连接设备。
7. 内置 createGroupWithRegisters 成功/失败，共 2 项：成功的 group→register→register 三次通知均在事务结束后，另一连接已能看到完整结果；中途 SQL 失败原图无损且没有通知。这是已管理路径的对照，不代表所有内置方法已逐一新增两连接测试。

每个 fixture 只有合成设备/组/点/告警；writer/reader 分别使用公开 SQLite 连接。锁超时仅在测试库设为 0；清理时先核验目录父路径、拥有者前缀和非链接类型。记录真实 net listen/connect/fetch 尝试和 unhandledRejection，均为空。审计读取源码以执行真实 API 中继注册，不依赖 Git 历史，不运行主入口。

## 为什么本轮不做隐式修复

- 抑制所有事务内事件会造成外层成功提交后没有任何同步通知，不能保持旧调用兼容；直接强制 COMMIT/ROLLBACK 又会侵占调用方事务。
- queueMicrotask/setImmediate/定时等待，以及事后 `isTransaction === false`，均不能区分提交、回滚、保存点回滚或换了一次事务，已有反例。
- 不截获私有 db.exec 来猜事务边界：prepared COMMIT、已有连接引用、保存点嵌套及异常回执都需要完整契约；本轮没有建立这种契约。
- 改为提交后通知会移动异常发生位置和订阅者顺序，并影响重入、同步失败、录制来源失效和旧返回行为。现有证明不足以对外部调用安全实施；不增加未接入的事件队列实验。

推荐后续是独立、显式拥有事务的可选入口，先定义哪些 primitive 可组合、哪些现有自管事务方法须拒绝嵌套；拥有者在确定提交后按定义顺序发送事件，确定回滚则丢弃本次事件，未知提交/回滚保留原错误与结果待核实。需要覆盖嵌套保存点、订阅者重入/失败、关闭/重开、录制 guard/lease、缓存与通知兼容，不应只加一个通用 transaction(callback) 包装所有方法。未经设计不要自动补发旧写入、恢复来源、重连或重录。

现阶段继续使用已有自管事务接口，不在自定义集成中访问私有 db 包裹多个调用。同步事件只用于触发重新核实；它不是持久事件日志、操作成功凭证或跨连接快照保证。
