# 退出信号隔离审计与接入决策

基线`5160cd3f3cfb287a667c95517ccf2c98d47a5994`，开始时工作区干净。要求是在隔离子进程验证SIGINT/SIGTERM、重复信号和清理失败，并且只有不改变现有启动/退出语义时才接入。本轮结论：**该条件尚不能保证，不修改主入口，只提交可重复审计和设计缺口。**

## 现有入口与平台事实

只读审查apps/cli/src/main.ts：端口预检发生在Context/数据库创建之前，失败显式exit(1)；随后按现有顺序注册插件、空配置seed、初始化从站内存、startAll和listen。没有SIGINT/SIGTERM处理、统一启动失败finally或全局存储ready屏障。本轮没有导入或运行它，没有改插件顺序、DATA_DIR、端口、seed、采集或异常处理。

当前验证平台为win32、Node v24.18.0。Node 24文档说明：信号监听可能移除默认行为；Windows的程序化SIGINT/SIGTERM kill会强制结束目标进程，终端Ctrl+C是另一种信号来源。exit回调不能完成异步清理，beforeExit也不是处理所有显式退出的替代方案。[Node 24官方信号与进程事件文档](https://nodejs.org/docs/latest-v24.x/api/process.html#signal-events)。这些平台说明与本机实测分开记录，不用文档推断实际终端已验收。

## 可重复的隔离方法

新增白名单test-signal-exit-audit及仅供它使用的signal-exit-audit-child.mjs。fixture只导入node:process，仅有模拟api/store/config关闭计数、两条模拟待写记录和保持事件循环的计时器；没有数据库、协议、驱动、模型或应用模块。

父测试用fork创建每个子进程，清空继承的Node启动参数和非必要环境，cwd/用户目录/数据目录都指向新建临时目录，windowsHide=true。信号只发送给自己持有的ChildProcess句柄；不枚举PID，不向测试外任何进程发信号。每个用例都有期限和回收，父进程断开时fixture自行退出。生产入口只作为文本检查，从不执行。

严格区分两类交付：

- `owned-child.kill`：真正调用当前平台的ChildProcess.kill，只验证Node/OS该接口的结果。
- `synthetic-event-only`：父进程通过IPC要求fixture执行process.emit。它只证明JS监听分支、等待和错误策略，**不证明OS、终端或服务管理器将信号送达**。

## 本机实际结果

| 用例 | 观察结果 | 对接入的含义 |
|---|---|---|
| 原生child.kill(SIGINT)，baseline及已注册监听候选各一个子进程 | 均为`{code:null,signal:'SIGINT'}`；没有进入清理 | 监听器不能拦截本平台此强退路径 |
| 原生child.kill(SIGTERM)，两种fixture | 均为`{code:null,signal:'SIGTERM'}`；没有进入清理 | 不能承诺Windows服务stop/kill会flush |
| baseline合成SIGINT | emit没有处理者，不触发默认信号退出；由测试显式stop后code0 | 单独process.emit不是原生信号验收 |
| 候选合成SIGINT/SIGTERM，清理成功 | mock api/store/config各关闭一次，待写计数0；数值code130/143 | 证明候选JS分支；这不是上面原生退出的同一可观察结果 |
| 首个SIGINT，清理暂停时再合成SIGTERM，策略合并 | 清理一次，最终code130 | 改变原来立即退出/重复信号时的等待行为 |
| 同样重复信号，策略第二次强退 | api计数1、store/config计数0，模拟待写2，code130 | 更快退出的代价是未完成清理，不能默认采用 |
| 清理失败，保留首信号原因 | mock仍尝试各资源，保留错误和模拟待写2，code130 | 退出码本身区分不了清理成功与失败 |
| 清理失败，专门退出码1 | 同样保留错误/待写，但code1 | 改写首信号143的含义，需要明确策略 |
| 候选模拟启动失败及store清理同时失败 | code1，两条原错误都保留，各mock仍尝试关闭 | 仅证明候选错误归并，不是实际主入口初始化验收 |
| 候选清理完移除监听再向自身发SIGINT | 本机父观察为`{code:1,signal:null}` | 不能据“重新发同一个信号”声称恢复了原生退出结果 |

共13个独立fixture子进程用例通过断言。表内待写记录是mock计数，不是对实际DuckDB损失行数的测量；真实存储的最终flush和错误保留仍由上一阶段资源生命周期回归验证。

## 推荐决策及缺口

当前保持应用入口不动。直接加process.on再await close，会替换默认退出并引入等待；在失败或重复信号时，无法同时做到“保留默认退出原因”“用状态码明确清理失败”和“未落盘数据不会被强退丢掉”。当前mock证明了不同策略的后果，没有得到无语义变化的通用实现。

下一步需要明确：

1. 实际运行方式和停止来源：Windows终端Ctrl+C、npm/tsx进程层级、服务管理器或POSIX环境。应在对应受支持的隔离环境验收；本机child.kill结果不能推广到这些来源。
2. 首个信号是否允许等待，以及挂起的查询/OTA/transport如何处理；不擅自添加固定超时后强关、取消硬件升级或丢缓冲。
3. 重复信号合并还是强退；如果强退，如何提示未落盘风险。不能把强退当作正常清理成功。
4. 清理失败返回1还是保留首信号退出原因，以及保留store引用/待写副本的处理方式；不能仅依赖框架dispose返回，因为部分错误会被框架记录。
5. 若未来接入，需对真实入口建立可注入且可隔离的启动测试边界：捕获配置/存储引用，阻止停止请求之后继续seed、设置从站值、启动采集或listen；保留当前端口预检、插件装配顺序及故障降级政策。模拟启动错误不能替代这些证明。

本轮没有新增生产信号适配器、退出端点或未接入的基础设施，也没有修改旧信号、启动失败或进程管理行为。
