## 复现与语义

45阶段只比较规则字段。同一点位由uint16改成uint32后，旧窗口仍能写入按旧dtype编辑的阈值；预期409的离线断言在旧实现失败。本轮把原规则和原点位/来源值一起核对，不改告警策略。

规则引擎按点位functionCode/dataType/地址解码原始值；主站选择所属分组的从站，设备从站模式选择设备slaveId。factor/offset、单位、枚举和显示小数不参与比较。基于现有语义，context v1含点位ID/设备ID/分组ID、FC/地址/dtype、分组FC/范围/数量/读写模式、设备ID/角色、有效从站及当前transport实际连接字段。TCP只比较IP/端口，RTU只比较路径/波特率/校验/数据位/停止位/流控。

名称/别名、倍率/偏移/单位/枚举/小数位、quantity点位备份元数据、启停/周期/超时/保留策略、闲置传输字段不属于本条件。主站的闲置设备默认从站、设备从站模式下闲置的分组从站不阻断原始值告警编辑。上下文是明确的小型只读副本，不回传大型枚举或模型设置，不证明配置通过了协议/点表诊断。

## 服务端与界面

共享capture/parse函数冻结规范字段、检查ID关联与完整性，拒绝未知版本、缺失/异常字段和多余上下文字段，不猜从站或缺失参数。规则修改/删除在原BEGIN IMMEDIATE内比较原规则及context，并在SQL后、提交前再核对点位/来源；变化409，读回不一致回滚。新createRuleSettings同样在锁内比较、插入、读回及提交，提交后通知失败只给警告，不冒充写入失败。没有新增数据库列或迁移。

新界面在告警窗口打开时固定point/group/device条件；后台刷新、重选规则或放弃规则草稿都不会悄悄刷新来源条件。可核对的当前配置不同时提示变化并暂停新增/保存/删除，配置不完整时保留草稿并暂停，恢复同一完整条件可继续；真正改变来源须记录草稿、关闭、刷新配置并重新打开。服务端仍核对，防客户端刷新延迟/请求期间竞态。原规则字段与待核实写入状态的45阶段保护保留。

新界面始终传context且要求成功响应protection=rule-and-context，旧服务/缺标志/较弱响应不能冒称保护成功，无自动降级或重试。新增没有幂等键，条件匹配不阻止重复新增，响应不明仍须先只读核对。

## REST/MCP兼容

- GET /api/rules/:id/settings返回原expected及expectedContext；GET /api/registers/:id/alarm-context返回新增用条件，使用同一只读事务，Cache-Control:no-store，不写操作日志。
- PUT/DELETE /api/rules/:id/settings允许原expectedContext；字段出现时必须完整有效且对应原rule.registerId。提供条件时成功响应增加protection=rule-and-context；缺context的旧规则级请求保留45阶段请求和响应形状，只保护规则字段。
- POST /api/rules/settings请求{fields,expectedContext}，fields仅registerId/operator/threshold/message，强条件必需；原POST /api/rules及旧PUT/DELETE /api/rules/:id语义保持，外部旧REST仍无来源/并发保护。
- MCP get_alarm_edit_context只读，rule_id/register_id二选一。create_alarm_rule可传expected_context；update/delete可同时传expected_rule与expected_context。部分/NULL/非法条件拒绝，不落到旧路径。条件分支在首段JSON返回protection；通知警告追加文本。新注册器使用既有类型适配器并纳入服务类型检查，实际SDK协议验证。
- 完全不传条件的旧MCP调用保留旧行为和首段JSON，追加明确兼容警告；未把无法推断的旧用户意图冒充成新快照。其内部旧读后写仍有并发窗口，跨调用/跨轮次更无保护；调用方应升级。警告表示保护范围不足，不等于本次没有执行，不可因此自动重放。
