# 配置提交代际事务契约的隔离证明

基于d23ed7f，选187号方案中的第一个可独立验证步骤：**只证明提交代际与生命周期契约，不把它安装到生产配置库**。本轮没有增加ConfigStore方法、业务表、触发器或迁移入口；新界面继续阻止发送。

## 第一阶段契约

在只含合成candidate_sources和candidate_generation的SQLite库中，定义以下要求：

1. 配置行和提交代际在同一事务内变化；提交的A→B→A即使最终内容相同，也不能复用原代际。删除后重插相同ID/内容同理。
2. 回滚、语句失败及嵌套savepoint回滚一起撤销尚未提交的数据与代际。事务内不能发布可供写入使用的观察票据，匹配也保守返回false。
3. COMMIT确实失败而事务仍在进行时，不发布新代际；只有确认回滚后才能重新读取。提交后通知失败不能撤销已提交版本，也不能把操作变回“未执行”。
4. 票据还属于明确的连接/运行生命周期。恢复旧库、重开或重建可让版本和内容重新相同，必须失效旧生命周期；仅持久计数不足以处理恢复的ABA。
5. 旧库无元数据、错误类型、连接关闭或计数耗尽时，条件能力不可用，不能猜默认代际。旧普通配置写入不因此被改造或禁用。

票据只是脚本内的冻结对象和WeakMap拥有者，不是新REST协议、持久操作记录或鉴权。观察匹配不是最终发送原子锁；读取返回后仍可发生配置变化，不能据此恢复GUI写入。

## 实现范围与实际证据

仅新增scripts/test-config-generation-contract.ts并纳入严格services类型覆盖及安全测试白名单。脚本内DDL/触发器明确只命名candidate_*，不是对真实配置表的迁移。普通场景使用:memory:；跨连接场景只使用专用临时目录下新建的synthetic.sqlite，关闭后检查目录归属再清理。

| 场景 | 证明的有界结论 |
|---|---|
| 提交ABA、ID删除/重建 | 合成触发器推进提交版本，旧票据失效，源值相同不能代表同代际。 |
| ROLLBACK、SQL失败、savepoint | 版本与配置数据原子恢复；未提交票据不发布。 |
| 真实COMMIT失败 | 使用SQLite延迟外键约束制造提交失败，确认事务仍活动、不能发票据，ROLLBACK后数据/版本恢复。不是仅在commit前抛一个JS异常。 |
| 提交后通知抛错 | 模拟通知异常，但真实SQL已提交；新版本保留，旧票据失效。不代表所有生产通知路径已重新审计。 |
| 合成DDL逐步失败 | 五个安装步骤分别故障注入，事务回滚后无半张代际表/半套触发器，原合成配置值保留，可重新安装。这里只验证未来迁移应具备的性质。 |
| 重复安装、类型错误、耗尽 | 不重置已提交版本；错误元数据不静默修复；样例选JS安全整数边界并在耗尽时失败，不回绕。这是fixture表示选择，不给现有配置字段添加限制，生产表示仍待设计。 |
| 两个临时连接 | 另一个连接的提交ABA被代际发现；另一个连接的回滚不冒充已提交变化；重开后的观察拥有者不能沿用旧票据。 |
| 恢复负对照 | 故意把计数/内容恢复成旧状态且不失效生命周期，旧票据会匹配；显式失效后才拒绝。测试通过表示此缺口被准确复现，不表示现有生产恢复路径自动具备保护。 |
| 真实ConfigStore对照 | 仅新内存库：实际getGroupSettings的内容revision在已提交组从站7→9→7后重复，等内容重建也重复；reopen的录制scope变化。证明现有哈希不能当提交代际，未给生产增加代际。 |

本轮没有对SQLite所有并发模式、恶意DDL/元数据改写、数据库文件替换或原生发送窗口给出证明。支持写者必须遵守经过审计的版本维护；有能力移除触发器或重写元数据的管理操作不能被默认为普通配置写者。未来恢复/重建调用必须与生命周期失效一同接入，不能仅复制本脚本的counter就宣称完成。
