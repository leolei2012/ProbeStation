# 实际SDK队列发送门与取消锁边界

基于34dc3b4，继续183号的有界审计。本轮仅测试和设计，没有生产锁、版本机制或来源保护接入，也未修复182号的数值写入风险。

## 从抽象sink推进到已安装SDK

`scripts/audit-write-send-boundary.ts --mock`使用当前已安装jsmodbus 4.0.10的实际TCP/RTU客户端和请求队列；只把网络/串口换为内存Duplex。拒绝其他参数，禁止listen、socket.connect、fetch，不打开库或设备。版本断言要求升级依赖后重新审查，而非假定内部行为稳定。没有安装、修改或patch依赖，没有访问SDK私有成员。

已读实现：`client-request-handler.js`的registerRequest先排队；_flush启动当前请求计时器后才调用socket.write。TCP客户端等待连接亦有异步窗口。库的公开接口没有传入每操作版本/来源的发送前回调。驱动现有recordTx在调用客户端前记录，不能作为实际发出、设备接收或来源校验的证明。

实际SDK+模拟流证实：

- 前一写请求未收到响应时，第二写保留在SDK内部队列。接纳后变更版本，再回显前一响应，第二写仍进入模拟流。
- 把代际门放在内存流的_write中，在唯一模拟帧记录前同步核对，能阻止已排队旧代际；代际递增也拒绝A→B→A。只比较最终内容的门仍放过ABA。
- 这只证明受控内存sink的最终边界。真实net.Socket/SerialPort的原生缓冲、库内部调度、内核提交和物理发送未验收，不能把_write实验当作生产可patch方案。
- 两次不同版本的相同RTU写，其原始字节完全相同。只按帧内容匹配ticket/版本会歧义；需要操作拥有者和受控队列携带身份，不能从地址、值或时间猜测。
- 两个RTU从站客户端共用同一模拟端口时，可在首个回执前各发一帧；各自的客户端队列不提供端口级串行化。不能用单从站/单客户端锁代替整个串口的控制。

## 哪些边界可在受控范围成立

| 路径 | 本轮证据及必要条件 |
|---|---|
| 仍在自有队列、未调用SDK | 能撤销自有等待任务并证明零模拟帧；不能把此结论用于已经进入SDK的请求。 |
| TCP/RTU全部操作经过同一通道许可 | 实际SDK对照中，许可保持至原SDK promise结束，第二任务仍停留在自有队列；代际改变后可在SDK接纳前拒绝。未变更对照顺序完成。前提是所有读写、连接重建、OTA/raw socket等都参加，且连接后的版本核对与最终提交边界可证明。当前生产未满足此完整前提。 |
| SDK内部已有排队任务 | 受控模拟sink的最终代际门可拒绝；仅在路由、采集器入口或SDK调用前检查不够。生产需要公开稳定的按操作提交边界，不能靠patch私有队列或全局覆盖socket.write冒充解决。 |
| RTU共享端口 | 需要串口级拥有者、所有从站客户端及原始写共同协调；取消一个操作不得释放其他操作仍占用的总线。没有证明生产已有完整覆盖。 |
| 本地从站内存写 | 源码中sync后紧接server.write有潜在同步边界；本轮没有运行其发送/版本对照，仍未纳入候选支持，不据此称已保护。 |
| 多进程/绕过公开配置写入/静默ABA | 183号通知计数和内容哈希不构成权威版本。本轮没有新增持久化版本或迁移；应先界定受支持写者范围和原子版本维护，否则新条件写必须拒绝。 |

以上不是现有任何生产路径已安全的结论。若未来明确限定单进程、所有配置及I/O写者可控，短同步校验/提交区与不复用代际有条件可行；不能为兼容旧路径而假设它们都遵守新锁。OTA目前实际调用getRawSocket，必须纳入评估。

## 取消、兼容与死锁

Promise.race等待AbortSignal只停止调用方等待，实际SDK请求仍排队并可稍后发出。实际公开manuallyClearRequests对照也未移除后续排队项：当前拒绝后回显旧响应，下一项仍发送；不能以该方法回执推断所有待写已撤销。

同一内存流close对TCP和RTU并不等价：TCP客户端进入offline并清理等待，当前RTU请求处理器未绑定同样的close处理，状态仍online，promise依赖计时器逐项失败。模拟流destroy阻止了后续帧，不证明真实端口已无原生缓冲或已发请求被撤回。不能用关闭整个共享端口选择性取消某个ticket；会影响其他读写，结果也可能未知。

锁模型实际建立了两条未决acquire：编辑者持配置锁等通道，写者持通道等配置，形成循环；没有阻塞进程等待超时，取消其中一个等待后按拥有者清理。另验证重复release与拒绝重入。不把取消等待当作释放已有通道。

设计建议：配置临界区不跨连接、排队或响应await；统一锁顺序，校验时若无法获得所需短许可应失败或在尚无副作用的自有队列等待。异步诊断/回调不得在持锁时重入获取同一锁。仅在enqueue后立刻释放许可，会留下SDK内部队列；持有到回执虽便于串行化，却有超时/吞吐和长占用成本，需有界等待、拥有者追踪与明确清理，不能盲目提前释放或自动重试。

旧REST/MCP/驱动协议本轮完全不变；旧无条件调用风险继续存在。未来条件能力需要独立识别并避免旧后台静默忽略条件；发送前可证明未接纳才报告未发，进入底层或回执丢失应保守报告未知，不能声称硬件回滚、物理身份认证或旧接口幂等。
