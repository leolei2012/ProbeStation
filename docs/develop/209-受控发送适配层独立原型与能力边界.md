# 受控发送适配层独立原型与能力边界

> 状态：独立隔离原型，2026-11-11，基于e323ffc；没有生产接线或条件写API，GUI仍禁写，旧API不变。目标是验证可行的不变量，不宣称实际硬件安全已经解决。

## SDK及入口确认

当前安装的jsmodbus 4.0.10在请求注册时编码从站与请求体，内部_flush再调用流write；没有公开的逐操作配置版本/连接代际发送前钩子。socket.write回调错误只记debug，不能直接变成可信的“本操作未发送”回执。此前本轮前置6例证明旧请求仍带旧unit7、Writable缓冲不等于目标改成9，以及模拟拒绝后TCP得到Offline、RTU得到Timeout。不能只由这些错误名推断是否已发。

本轮生产apps/packages与e323ffc无diff；重新运行实际SDK25组审计与配置AST（26个run、65个exec位置）。208号设备/分组/点位、导入/恢复/录制、旧REST/MCP、从站内存、OTA/raw socket入口族及其未保护边界仍适用。这里不是新增全仓库形式化覆盖。

## 原型做了什么

新增`scripts/test-controlled-send-adapter.ts`，没有导出AdapterModel供产品调用；类型检查及安全白名单登记它。只创建自有临时SQLite、内存Duplex和实际TCP SDK客户端，禁止真实listen/connect/fetch，不接受数据库路径或其他参数；未安装依赖。

- 自有FIFO队列在SDK外等待；不透明票据只在创建它的模型实例有效，内部绑定唯一operation ID、版本、从站/地址/最终uint16字和连接代际。每个已尝试身份只能消费一次，不按帧内容猜身份、不自动重放。
- 通道能力默认不可用。测试显式提供“独占通道”假设后，仅支持TCP/FC06单字；其他FC、无效值直接不能准备。这个fixture布尔参数不是生产能力发现机制，不能做成用户可切换的解禁开关。
- 在共享临时库channel行以条件UPDATE认领唯一owner；不在整个等待响应期间持数据库写锁。不同进程必须自愿使用同一数据库/认领契约，否则模型不适用。没有TTL、自动抢占或过期重试。
- 每次操作创建自己的SDK与私有内存流；最终_write闭包绑定该操作身份，短BEGIN IMMEDIATE内重新比较配置/版本、连接代际、通道owner及取消状态，紧邻唯一模拟帧接纳点。没有修改SDK、patch真实socket或读取私有队列。
- 只有拥有者CAS能够释放通道。发送前可证明未接纳为not-sent；已经接纳后超时/取消/断线为unknown，持久owner继续保留，阻止后续实例发送。模型不提供自动解锁/恢复；旧token不能用于重试。

这使用简化的source/version/channel测试表，不是208号三表迁移方案的生产安装，也不重复其实际ConfigStore迁移兼容证明。模型省略完整配置schema完整性、64位版本耗尽/恢复、跨文件身份和真实传输生命周期；这些前置依赖仍需208号契约及后续实现。

## 15组实际SDK模型验证

1. 默认能力不可用、非FC06和非法值不可准备。
2. 模拟帧确实为预期unit7/FC06/地址0/值42；伪票据及已消费票据不产生第二帧。
3. 独立进程已提交ABA后最终拒绝，零帧。
4. SDK外等待时另进程改变地址，私有流最终拒绝，零帧。
5. 外部已有owner不抢占、不超时解锁。
6. 另进程不能抢已拥有通道；接纳后配置仍可变化，不把锁持到回执。已接纳字节继续绑定原unit7，这不算“改发到新从站”。
7. SDK前连接代际改变，零帧。
8. 通道owner被替换后拒绝，不能误清除新owner。
9. 两个完全相同的SDK帧仍对应两个不同操作身份。
10. 发送后无响应是unknown，第二适配器实例也无法认领被隔离通道。
11. 接纳前取消，零帧。
12. 接纳后取消，unknown且保留隔离。
13. 接纳后断线，unknown且保留隔离。
14. 第二任务仍留自有队列时配置变化；第一项完成，第二项拒绝，仅一帧。
15. 自有队列等待中取消，零新增帧，旧身份不能再执行。

所有“帧”均为内存记录，所有completed均为SDK收到模拟回显，不代表设备已执行。真实套接字的接纳、内核缓冲、串口排队、物理身份和线路结果没有验收。构造内存Duplex的_write是测试sink实现，不是给真实驱动添加同名patch的许可。

补充独立内存反例：两个新TCP SDK客户端都从事务号1开始；第一条写值11的旧响应被故意送进第二个写值22的客户端时，第二个Promise仍解析成功。这不是现有生产缓存客户端发生该故障的证明，而是未来桥接不能乱转发回包的证据。模型每操作私有流只接收自己生成的模拟回显，未覆盖这个真实路由问题；不能将模型的completed升级成可信设备执行回执。实际接入必须绑定真实连接/操作及完整响应，并拒绝歧义，不能仅凭事务号或SDK Promise成功释放安全结论。

## 为什么仍不能接入生产

| 缺口 | 必须证明后才可声明能力 |
| --- | --- |
| 独占拥有者只是fixture前提 | 实际所有读写、重连、共享RTU、OTA/raw socket及旧调用都参加同一调度；不同数据库/其他控制程序不可绕过。保持旧协议不等于可以假定其内部遵守新锁。 |
| 每操作私有内存流 | 真正连接转发、响应路由、错误和销毁必须绑定同一真实连接代际；不能把实际共享socket暴露给未知写者。SDK没有原生条件钩子，不能靠原始帧匹配操作ID。 |
| source版本表是简化模型 | 所有受支持配置DML须同事务持久递增，DDL完整性、文件替换/整库还原及所有写者生命周期须有可信实例身份；真实库未安装。 |
| unknown后的持久owner | 崩溃会留下阻塞，这是失败关闭的可用性代价；安全恢复需要确认旧发送拥有者已被隔离及不再提交，不能按租约时间到期就抢占。模型未实现恢复。 |
| 同步模拟临界区 | 不能在持锁时await、调用可重入用户回调或把配置锁保持到设备响应；生产锁失败/提交错误与已接纳副作用的分类还须故障注入。模型没有证明任意DB/OS异常的可靠回执。 |

下一项可行工作应先选择一个真实TCP受控连接实现，建立独立的操作流/响应路由及通道拥有者契约，继续仅用进程内传输模拟。即使TCP成立，RTU、本地从站、OTA及无法纳入的旧入口仍保持条件能力不可用。无需也不得为验证本原型开启GUI或调用现有旧写API。
