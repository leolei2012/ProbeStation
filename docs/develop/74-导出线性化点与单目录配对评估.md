# 导出线性化点与单目录配对评估

## 推荐决策

基于干净的`94d9909390171619ea527c9c8ba11dbf73c1962e`，有界检查73号两个缺口。本轮**不接入生产、不新增服务或审计命令**，只扩展已有内存审计并记录结论：

1. 可以将最终同步验证中的配置事务快照读取点定义为逻辑批准点P：文件消费同一预期定义、原实例/打开周期仍有效，P之后的编辑不追溯撤销已批准附件。这是可测试的有限承诺。
2. 不能把P称为“首字节/最后字节发送时配置仍未变”。现有Fastify压缩和其他异步onSend步骤可能在P之后、真正发送之前执行。若产品要求配置冻结到传输结束，本轮不能保证；不建议跨网络持有数据库写锁。
3. 当前CLI能证明启动时把同一DATA_DIR内的两个文件路径交给config/store，但这只是装配声明。当前内存scope与持久化数据模型无法从已有内容推断历史库和配置的共同来源；不能把同目录、同ID或都ready当成历史身份认证。

因此建议后续先明确采用“P时已确认定义＋本次装配声明的实例”这一有限契约，再验证实际启动拥有关系与新只读调用协议。保留旧接口，不扩大Workspace，也不为追认旧库而写共享身份/迁移真实数据。当前条件导出仍未启用。

## 证据与交付边界

本轮只读当前安装Fastify 5.12.0与@fastify/compress 9.2.0源码，以及项目API装配源码；没有联网获取其他版本或启动主程序。相关位置：

- `packages/api/src/index.ts`先await注册全局compress，再定义导出路由。隔离测试版还有自己的异步onSend HTML横幅钩子；不能仅看导出handler就推断发送链已结束。
- `node_modules/fastify/lib/hooks.js`的onSendHookRunner遇到Promise会等待后续调用，最终才进入reply发送逻辑。
- `node_modules/fastify/lib/reply.js`的onSendHook/onSendEnd：字符串/Buffer在钩子后设置响应头；流则走sendStream，实际头发送还受流事件影响。
- `node_modules/@fastify/compress/index.js`通过onRoute将自己的onSend**追加**到路由钩子列表；不能假定自己声明的route.onSend就是整个链最后一个。

逻辑P应指最终同步校验中实际取得配置快照的读取点，而不是一次哈希完成、调用reply.send或收到下载的时刻。SQLite读事务提供同一图；本进程JS在该同步读取期间不会调度另一个JS生命周期操作，但外部写连接仍可能在P之后提交。校验结果只说明P处条件相等，不说明从预览到传输结束连续未变。ABA仍是当前值条件，不是单调revision。

## 本轮可控测试

继续运行现有`npm run audit:sink-condition`，全部config/store严格`:memory:`、Fastify仅inject、不listen；无硬件、真实库、Workspace、MCP或模型。新测试不调用完整API/main启动。

### 错误响应清理

测试handler先拿到真实Sink候选结果并设附件/条件回执头；较早异步onSend再改别名，随后同步guard发现不匹配：

- 仅传error给Fastify：HTTP409，但Content-Disposition和成功条件回执仍在。说明“抛错必然无附件头”在onSend阶段不成立。
- 显式清除成功附件/回执及相关长度/编码头，再交错误处理：HTTP409、JSON、无附件/成功回执；一次性消费验证上下文，避免错误响应再进入guard无限循环。长度/编码清理属于保守处理，本测试主要断言实测存在的附件/回执头。

这只是测试内候选处理，未改产品的错误处理器或现有路由。

### 逻辑批准与真实发送的差别

用真实内存store写201个时间点，让真实Sink生成超过默认压缩阈值的CSV；按生产方式注册全局compress。路由onSend同步validate时，断言headersSent=false，记录approved；后续异步onSend await后修改配置，仍断言headersSent=false；最终inject收到gzip HTTP200，解压CSV确实是原point定义的202行（含表头），而当前条件已变化。

这同时证明：P可被观测且原文件符合P处确认定义；P不等于物理发头/网络传输时刻。若采用有限契约，该后续编辑可在线性化顺序中排在批准之后；若要求“发头时也必须还是原配置”，该测试就是反例。inject不模拟真实TCP/代理/背压/客户端断连，不据此承诺用户已接收到文件。

## 单目录配对能够与不能证明的事实

- CLI源码以同一个dataDir构造`config.db`和`poll.duckdb`路径，并将同一Context的config注入store及Sink；未注册Workspace。项目apps/packages中实际reopen调用仍只在保留的Workspace方法里，没有在当前CLI/API链路发现公开切换。
- ConfigStore构造同步打开并迁移配置，store构造则发起异步init；await注册插件不等同于两库原生初始化都已成功。现有store捕获句柄会在未就绪/失败时拒绝，这是局部能力，不是启动共同身份。
- 配置snapshot的configurationScope和storeScope都是进程内打开周期标识；poll_data保存object_id、采样批次和从站，不保存共同配置库身份或历史配置revision。不能拿batchId或时间戳补出库配对。
- 本轮完整重跑既有内存反例：保持配置scope，独立重开store并写200，旧条件拒绝，但新preview/候选接受200。它证明“请求时重新组合状态”不能判断原始共同拥有关系；不代表当前在用CLI实际开放了该操作。

如果将“配对”定义为本次启动声明使用这两个路径，则可在拥有打开动作的装配流程中建立并记录这一声明，等待双方成功后绑定原实例/周期；独立重开/替换即失效，不能请求时自动重配。如果将“配对”定义为两库历史上一直同源，则当前格式没有足够证据，必须保持未知，或另经用户明确的数据治理方案；本轮不引入新表、不回填旧身份。

## 进入实现前的最小门槛

只在契约范围确定后，验证实际单目录启动的成功/部分失败/原实例绑定；再将同份配置的条件collect、完整附件及验证上下文接到可选的新路由，拥有明确的逻辑P。路由必须在所有等待后复核，并正确清理失败时已设成功头；成功回执只声明P的条件，不声明传输期冻结或历史物理归属。压缩/钩子顺序及其升级要有组合回归。

旧GET/MCP仍未受新条件保护；前端已见变化保护保留。本轮停在正确性边界，没有权限阻塞，不把更多未使用的基础设施当作解决方案。
