# 生产删除调用链与事务边界验收

基线 `1470bdaf1ed2d41adb59a8122bffd934ef7a6cfd`，初始工作区干净。本轮只增加静态/隔离审计、已有删除回归的入口断言及说明。生产代码、事务、通知顺序、API/工具协议和依赖均未改。

## 明确结论

**生产中确有外层事务调用删除，但已找到的路径全部由 ConfigStore 自管，并在调用删除前设置 `restoring=true` 抑制中间通知。当前未发现公开路径触发127号审计中“未抑制通知的外部事务随后回滚”的问题。** 不能把这项外部集成限制描述成普通 REST/MCP 删除已知会发出未提交通知，也不能笼统说生产没有外层事务。

最小处理是保留已有批量事务门禁，增加可重复的边界证明，不再添加生产修复。外部自定义插件若绕过私有 db 开启事务，仍适用127号限制；本轮没有确认它们不存在。

## 反向入口与条件

- 旧 PUT /api/groups/:id → updateGroup → updateGroupRows → 数量缩小才 deleteRegister。新 PUT /api/groups/:id/settings 与 MCP update_group → updateGroupSettings → 同一内部缩容分支；新路径还核对revision及明确删除ID。
- REST POST /api/monitor_objects/:id/points/book 与 MCP import_points_xlsx → 实际 Sink.importPointBook(...,true) → applyPointBookImport → deleteGroup。XLSX解析在事务前完成，事务内build是同步函数；错误回滚，成功统一通知。Sink的replace=false模式另有追加对照，当前这两个公开入口均明确传replace=true。
- 助手的分组提案仅允许name/isActive；MCP set_group_active和备份恢复中的updateGroup也只修改isActive。虽然静态可到达updateGroupRows，但当前合法参数不进入数量变化的删除分支。备份是追加新设备，不通过此流程删除旧组。
- 源码未发现当前入口在调用这些方法前绕过私有配置连接开事务。公开自管事务方法也不能据此视作可任意嵌套；失败/提交回执未知及通知抛错仍遵循已有边界。

AST是当前源码的调用清单，不是任意动态JS的完备证明。不涵盖外部插件、Reflect/eval任意拼接、修改后的依赖、旧dist或在用服务器代码；未访问192.168.90.137实例，也不把本地HEAD当作其已部署版本。

| 场景 | 已验证行为 |
| --- | --- |

| Sink追加对照 | 不调用删除，保留旧组/点/规则并追加新图，完成后一次通知；不是当前公开入口的默认模式。 |
