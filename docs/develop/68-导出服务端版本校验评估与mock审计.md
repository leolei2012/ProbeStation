# 导出服务端版本校验评估与mock审计

## 结论与本轮选择

基于干净的 `a97b51d88fe923e59c2c9dd9782863b396381ca0`。新增独立校验接口可以保留旧客户端兼容，也不需要迁移历史数据。但现有服务尚无“同一工作区/配置/时序库会话内，校验后直接消费同一份定义”的契约。仅加If-Match、在导出前额外GET一次，或只哈希配置值，会产生未覆盖的成功条件。本轮未达到启用该保证的验证门槛，因此不修改运行逻辑；交付可复现审计和可分阶段落地方案，符合本轮不强行修改的要求。

没有权限或工具审批阻塞；未实施是基于下面已验证的契约缺口，不是把缺失的校验当成完成。现有前端已知变化保护保留，后台未同步变化仍是已知限制。

## 当前契约

| 调用路径 | 已核实行为 | 兼容要求 |
|---|---|---|
| GET /api/export/csv、xlsx | object_id/start/end/register_ids/tz；未定义配置版本条件。ids仍沿用旧宽松解析；空/缺失选择及缺失ID有既存兼容行为 | 不改旧路由语义，不把旧客户端强制升级；若提供新版本条件，须明确能力及成功回执 |
| Sink.exportCsv/exportXlsx | collect先复制当前点位/来源，再等待原始查询，后续用同次副本；未接收expected版本 | 版本检查必须与这份副本在同一collect内完成，不能检查后再调用会重读配置的旧方法 |
| MCP export_history | 先校验所选ID、await store.flush，再调用上述Sink方法；无preview/expected参数 | flush期间也可能变化，不能把先前ID检查当版本保护；新能力需在实际消费处校验，旧工具兼容保留 |
| 配置读取 | ConfigStore已有getGroupSettings/getRegisterSettings事务快照范式；没有整个导出设备图的公共一致快照方法 | 需封装新的只读事务方法，不能从外部访问私有db，或逐组多次读取后冒充同一快照 |
| 隔离测试版 | 共用导出GET；onRequest默认拒绝GET/HEAD以外的方法 | 若新校验协议用只读POST，需精确允许新增路由，保留其他写入禁用；不能放开所有POST |

没有读取远端、凭据、真实库或注册表。工作区服务只读了源码，没有实例化Workspace或调用真实switchTo。

## 可重复的风险审计

运行 `npm run audit:export-version`。工具只接受固定--mock，不接受服务地址、数据库或工作区路径；全部配置和数据均为内存假对象，实际Fastify路由仅inject，不listen，不下载文件。它刻意验证已知缺口仍存在，输出 `KNOWN GAPS REPRODUCED; NOT A SAFETY PASS`，不加入npm test白名单，不能用退出0声称产品已防护。

实际结果：

1. 假后台源1值10变为源2值200，页面context故意保持旧值；真实downloadHistoryExport仍接收并交给假保存器。这复现未同步窗口，而非上一轮已知变化保护失败。
2. 对真实旧GET发送旧If-Match指纹，CSV/XLSX均HTTP200、附件内容为200。当前路由不执行该条件；前端只加一个请求头没有意义。运行代理策略未验收，也不能据此推断代理会正确校验配置版本。
3. 测试内构造“单独比对指纹→等待→调用旧导出”的反例，比对后改源，随后得到200。该预检包装仅为设计反例，不是现有生产接口；证明需绑定check与use。
4. 从生产Workspace.switchTo提取实际方法体，所有目录、注册表、poller、config、store及事件副作用注入mock。方法顺序为stopAll→await store.reopen→config.reopen。在假reopen屏障期间，配置仍旧、假时序库已新，GET得到900且配置指纹相同。stop/start都是假计数，未停止任何真实服务。此为生产方法顺序的mock验证，不是真实数据库并发实验；尚未验证在用实例是否暴露或启用工作区切换入口。Store.readObjectRows源码等待其ready，但未绑定配置/工作区epoch，这也是设计必须检查的依赖。

同样的配置值不等于同一时序库。应把指纹用于定义相等条件，不把它称为物理设备身份或历史配置真实性。

本轮实际运行 `npm run audit:export-version`，退出0并明确报告四类已知风险；缺少--mock时按预期拒绝。修改后的 `npm run typecheck:services` 退出0，审计脚本已纳入类型检查。另重新运行 `test-history-export.ts` 与 `test-history-export-context.ts`，均退出0，保留现有CSV/XLSX及前端已知变化保护；仅新临时库/内存数据，无真实服务。

本轮没有运行代码修改，因此没有重新构建前端或把上轮91组结果冒充本轮全量验证。审计不等于防护回归，未加入安全白名单。提交前核对6个明确文件、空白/新增秘密模式、父提交及canonical blob清单，提交后核对内容与剩余状态。

## 推荐的兼容方案

### 一、建立只读快照及生命周期契约

将导出所用定义投影制定为带版本的共享契约，明确字段、null/默认值、排序、来源与64位/枚举文本保真。不能只把前端局部JSON字符串命名为server revision。ConfigStore在单次只读事务内读设备、所有相关分组和点位，拒绝缺失/重复选择；提交后返回独立副本。前端打开时的已见投影必须与服务端preview一致，否则要求核对后重开，不自动采纳新定义。

为配置和时序库配对提供不暴露路径的工作区epoch。切换开始即标不可导出，只有两库均确认后才发布新epoch；部分失败保持不可用，不在finally盲目恢复。Store读操作绑定开始时的连接/代际，并在等待或重开后拒绝跨代，不能在await之后换用新ready而继续旧定义。推荐发送附件前再次核对epoch，覆盖XLSX生成等待期间切换；过期返回无附件，不重试旧请求。不要为此持有SQLite事务跨整个异步时序查询。

这些可以是内存状态与只读方法，无需真实库迁移；但牵涉工作区和store生命周期，必须先单独完成mock/临时库并发验收，不能直接在在用库试。

### 二、增加独立preview与条件导出

保持旧GET及Sink旧签名兼容。新增有明确能力版本的preview/checked导出入口：preview核对打开时客户端投影，返回绑定对象/选择/区间/时区/epoch及规范定义的revision；checked导出在同一个collect快照中比较expected，随后只消费这份副本，不再调用会重读配置的旧collect。

条件不匹配返回明确409及机器码，不能返回附件或开始原始查询；切换中或生命周期不明返回不可用，不能吞异常。成功回执应带实际核对的revision，客户端必须检查；旧后端忽略头但没有回执不能当校验成功。哈希可用现有Node crypto，revision不是授权令牌，不替代访问控制。

大点表和大枚举不宜塞进URL/请求头。若采用只读POST传投影，需显式体积限制和独立错误码，测试现有10000点及大文本，不能静默截断/丢ID，也不能把定义体积超限冒充20万原始行超限。此处尚未制定未经验证的新上限。

### 三、显式能力接入与降级边界

前端保留当前已知变化/取消保护，同时准备并核对server preview；旧后端不存在该能力时，不能自动回退旧GET却显示“已校验”。新能力可先保持未激活，后续决定旧后端是否保留明确标注的手动未校验入口。现有旧客户端继续使用原GET；MCP按可选新能力另行升级，不扩大其权限。

条件成功只说明使用了双方确认的同一定义和会话，不冻结历史数据本身，不改变原NULL来源、混批、缺字和automatic_eligible规则，更不生成PASS/FAIL。内容哈希允许值恢复为原值时重新相等；如要求任何中间修改都使旧版本失效，还需覆盖所有写入方的单调修订，不能声称普通哈希已覆盖ABA。

## 启用前验收门槛及独立后续任务

1. 先完成快照/epoch/读代际：多组同址多从站、删除/改名/改类型、双连接并发、相同ID不同库、重开失败及切换中读取；仅新临时库或mock，无真实迁移。
2. 再完成条件导出：preview与打开投影不符、preview后修改、比较后I/O延迟、切库/部分失败、缺/伪造/未知版本、旧后端无回执，全都无错误附件；定义读取失败不退回旧逻辑。
3. 最后接前端/隔离版：确认失效/关闭/重开/迟到/取消/超时，旧客户端→新后端、当前客户端→旧后端；大点表、CSV/XLSX现有列/UTC毫秒/批次状态/原始行上限一致。浏览器验收须用获准路径，不绕过限制。

本轮不提前实现其中一半来宣称保护成立。未推送、部署、重启采集、操作实机、调用模型或修改真实用户数据。
