# 历史时间精度与输入时区

状态：已实现，完整离线检查通过；浏览器未验收。2026-11-06，基线`527aa23`。

## 已复现的问题

原历史引用经`HistoryNavigation`得到精确毫秒后，HistoryView先格式化为不含毫秒的本地输入字符串，再`Date.parse`。纯日期复现：`.987Z`少987ms；同一秒内的`.123Z–.987Z`变为相同起止时间，原本有效的864ms区间无法查询。即使仅补毫秒，在纽约夏令时回拨第二个01:30还会少一小时（`06:30Z`重新解析为`05:30Z`）。

本轮优先修复这个定位基础，再提供明确的UTC输入；不增加书签存储、后台接口或数据库迁移，不连接设备或读取真实历史。

## 现在的行为

- 引用和快捷区间以绝对毫秒为准，不经本地墙钟字符串重新推导。有效的手工输入在解析时也固定为一个绝对时刻；改变另一端不会重解释它。
- 时间框使用`step=0.001`，保留毫秒；支持“浏览器本地 / UTC”输入切换，分别显示两端对应的UTC偏移，并给出完整区间的UTC原值。
- 仅切换输入时区保持区间、查询URL、当前缩放、分页及A/B上下文不变，不主动重新查询。正常编辑日期仍沿用原查询生命周期；等价的原生控件规范化（例如省略`:00.000`）不当成改时间，也不会丢掉重复时刻的绝对身份。
- 已确定的时刻在主机本地时区改变后仍保持绝对身份；显示值按当前输入模式重新格式化。无效输入只是待修正草稿，没有可保留的绝对时刻。
- 手工输入检查日历与本地时刻回读，不把2月31日或春季跳时中不存在的02:30悄悄移到别的日期/时间。有无效字段时禁用时区切换，先修正；开始晚于结束时仍可切换输入模式后修正。
- 手工本地重复时刻沿用浏览器的既有解析规则，不猜用户想选第几次；用UTC明确区分。导入的绝对时刻不受此歧义影响。输入框下的偏移及UTC区间提供核对依据。
- “今天（本地）”继续按浏览器本地自然日开始，选择UTC输入也不改变这个快捷按钮的含义；最近N分钟仍为准确的毫秒时长。

## 范围与兼容

这里只控制历史页时间输入与查询端点，查询仍提交ISO UTC；修改输入区间会按原流程取消/替换旧查询。曲线轴/悬停、表格时间及CSV/XLSX的显示时区继续沿用原约定，UTC输入选项不表示所有输出统一改成UTC。导出捕获的绝对开始/结束毫秒保持准确；原固定offset导出策略、旧数据身份及采样/告警语义未变。

精度上限是JavaScript Date/现有服务的整数毫秒，输入超过三位小数不静默舍入；不能用来承诺微秒/纳秒采样。无效或HTML时间输入无法表示的日期不构造查询。没有自动纠正系统时钟/时区或写入系统设置，也不保存新的浏览器偏好。

`history-time-range.ts`提供不可变的字段/区间与转换；`HistoryTimeRange.tsx`复用原查询/取消按钮并显示输入模式、偏移和完整UTC范围。原只用于历史的分钟级格式化函数移除。HistoryNavigation的一次性意图和迟到点位处理保持原样。
