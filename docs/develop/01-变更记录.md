## quantity 保真方案（历史记录，后续已确认实施）（2026-10-28）

- 本轮仅诊断与方案，未修改生产代码、数据结构或 quantity 的行为。按授权，发现需要产品决定的语义矛盾后停止实施。
- 本轮验证：当前工作区 `npm run check` 退出码 0，类型检查、生产构建及 14 组现有安全回归通过；`git diff --check` 通过。这不表示 quantity 的保真缺陷已修复。
- 证据：产品点表契约 `docs/product/10` 第 I 列称“数量”为“该点字宽”；`codec.registerWidth(dataType)` 则独立返回 1/2/4，数据库 quantity 默认 1，createRegister 不写入它。XLSX 导出第 I 列读取 quantity，导入却不读取第 I 列；MBP INI 解析还将窗口长度写入 ParsedRegister.quantity，但应用导入时丢弃该字段。备份解析未校验点位 quantity。
- 冲突示例：现有 API 创建 float32 点位会得到 quantity=1，而实际解码需要 2 字。若现在强制 quantity 等于类型字宽，会使此前程序自己导出的合法配置无法恢复；若只保存独立数量元数据，其合法范围又不能从“字宽”说明推定。本轮不把字段强制匹配或改写为 dtype 宽度。
- **建议方案 A（待确认）**：本轮只把 quantity 作为备份中的独立数量元数据原样保存，不影响 dtype、轮询长度、读写和合并。旧备份完全缺字段时补数据库兼容默认值 1；显式值不进行字符串转换、舍入或按 dtype 重算。建议合法范围为整数 1–65536；该上限及其是否代表地址跨度需在实施前确认。选择此方案意味着数量与 dtype 可以不同，并需说明 XLSX 的“字宽”表述与当前行为不一致。
- **方案 B（较大范围，当前约束下不实施）**：将 quantity 统一定义为实际字宽，必须与 registerWidth(dtype) 一致。须先决定已存在的 float32/uint64 + quantity=1 配置如何兼容，以及旧备份缺字段时是否按类型推断；同时需要点表导入/导出契约调整。不能静默改写旧字段或只改备份入口。
- 方案 A 获确认后的最小改动：共享数量校验；备份解析对缺字段创建归一化副本而不修改调用方输入；createRegister 显式保存合法 quantity；restore 继续沿用已有事务和统一创建入口。无生产迁移，不修改硬件采样语义。
- 待落地回归：非默认 quantity=2/4 和与 dtype 不同的数量；旧备份缺字段；0、负数、小数、null、布尔、字符串、超上界和不安全整数；JSON 导出/恢复/再导出数量一致；预览失败无写入；含多个点位的晚期失败不损坏目标配置、无变更事件；实际解码字宽保持原值。选择 B 时回归必须改为其明确的旧数据兼容策略。

## pollOnce 重叠分组合并事件漏告警回归（2026-10-28）

- 先用真实 `pollOnce` + 纯 mock 驱动复现第二轮批次校验留下的回归：组 A 读地址 0 单字，组 B 读地址 0–1 的 uint32，合并事件按地址取第一个字会选出 A/B 混批，导致完整 B=65536 的 `>65535` 告警被误跳过（实际 0 次，预期 1 次）。
- 保留 `pollOnce` 单一合并事件和 `poller/result` 结构。告警在当前事件内按响应身份收集字，选择事件顺序中最后一个完整响应；不跨响应或事件拼字，不访问 latest 补字。最新完整响应质量异常或地址重复时保持未知，不回退更早值。既有告警阈值和无批次身份数据的兼容路径未更改。
- 回归覆盖 pollOnce 的 FC03/04、32/64 位 BE/LE、JSON 事件往返、连接释放及事件数量；另覆盖跨事件缺字、旧字混入新批次、多个完整批次的先后顺序、坏质量与重复地址不误解除/重触发，以及有效恢复。

## 二十八、OTA 快结束时 END 超时误判失败修复（2026-08-23）

症状：START/DATA 正常，最后发 END 停在 `verifying` 超时报 `failed`，反复超时。

- 根因（真机实测确认）：**设备对 END 是会回 ACK 的，只是慢**——END 阶段设备要做整镜像 CRC 校验 + flash 页写（当前老固件 `check_crc32` 为逐位实现，END ≈100~150ms；设备侧已改查表版 ≈15ms 但新固件尚未刷入）。而平台 `rawExchange` 对 START/DATA/END **共用固定 8s** 并非问题太多，真正是要给 END 一个**适中且明确的超时**覆盖这段慢 ACK；先前 8s 其实也该够，但确凿起见统一收敛到明确阈值，避免模糊失败语义。
- 修复（`packages/ota/src/engine.ts`）：
  - 细分超时并统一语义：`DEFAULT_EXCHANGE_TIMEOUT=8000`（START/DATA 单块，秒回）与 `DEFAULT_END_TIMEOUT=2000`（END，覆盖 ~150ms 实测 + 充足余量；仍能对「设备真不回 ACK / 断开 / 跳转」较快判失败）；`exchange` 增加 `timeoutMs` 参数。
  - **不再采用「超时补发 STATUS / 视作成功」的降级分支**——既然设备确实会回 ACK，就保持简单确定：END 请求在 ≤2000ms 内收到 `ST_OK` 即 `done`，否则（超时或非 OK）明确置 `failed` 并给出清晰 error。避免把真失败误报成成功。
  - `DEFAULT_END_TIMEOUT` 已带注释说明依据，可在顶部按实际设备微调。
- 设备侧配套：建议把 `check_crc32` 改为查表实现（END 从 ~100ms 降到 ~15ms），服务端 + 设备端一起做最稳。

## 二、数据模型变更（重要，测试需关注）

### 1. 时序存储按「地址」键控（原 register_id）

- 冷层 DuckDB 表：poll_data(object_id, address, ts TIMESTAMP, raw_value DOUBLE, quality VARCHAR)。
- 热层用 objectId:address 复合键（地址是每设备独立的，不能只按地址键控，否则多设备同地址互相覆盖、实时值会「闪」）。
- 单设备快照用 store.getLatestByObject(objectId)。
- 旧 poll.duckdb 会自动迁移（register_id 列改名 address），无需删数据。

### 2. 类型 = 显示方式（存原始字、展示时解码）

- 存储/轮询都按原始 16 位字；寄存器类型（int16/int32/float32/hex32…）只是显示/解释方式，改类型不会改历史数据。
- 解码器在 packages/core/src/codec.ts：
  - decodeRawByAddr() 数值（曲线/告警/MCP）
  - formatRawByAddr() + formatRegisterValue() 显示字符串（实时表/历史/导出，hex/bin 逐字）
- 效果：32/64 位寄存器在实时/历史/曲线/导出四处一致（例如 int32 地址 0+1 显示 305419896，而不是两个 16 位字）。

## 九、RTU 串口轮询静默卡死修复（对照 MC_BASE 反馈 ProbeStation_feedback.md）

### 症状（反馈）

- RTU 设备（STM32G474 bootloader，9600 8N1，COM3）读不到数据，且**无数据、无错误、通信灯不闪**三合一静默卡死；
  但 .NET 直连 COM3 报 Access denied，说明 ProbeStation 底层已占用串口。

### 根因

- `SerialDriver.connect()` 里 `await new Promise(...)` 只靠 serialport 构造函数的 open 回调来 settle；
  当「原生已开、binding.open 的 Promise 不 settle」时 open 回调不来 → `connect()` 永久 pending →
  `getDriver()`/轮询全挂，且 `sp.on('error', () => {})` 把最后的兜底信号也吞掉。RTU 又按串口串行排队，卡死会冻结整条串口队列。

### 修复

| 层 | 改动 |
|---|---|
| modbus | `SerialDriver.connect()` 加 `connectTimeoutMs`（默认 3000）超时兜底：超时即 reject 并尽力 `close()` 半开句柄；不吞 error（open 阶段 reject、运行期告警）；`Config` 新增 `connectTimeoutMs` |
| poller | 连接失败冷却 `connectRetryMs`（默认 5000）：坏串口/坏地址不每轮重建连接，避免 RTU 队列堆积；看门狗 `watchdogTimeoutMs`（默认 30000）：启用且有分组但长时间无结果无错误时主动发 `poller/group-error`（`No response (watchdog)`）；`Config` 新增两项 |

- 验证：`npx tsx scripts/test-rtu-timeout.ts`（open 永不 settle → 超时 reject + 半开句柄 close；open 失败 → 错误冒出来；正常打开 → 不回归）、`npx tsx scripts/test-poller-watchdog.ts`（读卡死 → 看门狗标故障；连接失败 → 冷却期内只重连约 3 次而非 14 次）。
- 既有回归：`test-rtu` / `test-loop` / `test-group-fault` / `test-device-toggle` / `test-disconnect` 全通过。

| config | `monitor_objects` 加 `poll_interval_ms`（INTEGER DEFAULT 1000）+ `data_retain_seconds`（INTEGER，NULL=跟随全局） |
| poller | 全局循环改为动态 `setTimeout` 重调度（间隔 = 所有启用设备的最小 `poll_interval_ms`，下限 1ms）；`pollObject` 的到期判断改读设备级周期（组级字段保留但不再读）；看门狗阈值同样改设备级周期 |
| mcp | 新增 `set_poll_interval(device_id, poll_interval_ms)`（校验 ≥1 整数）；`get_device_health` 加 `poll_interval_ms`/`data_retain_seconds` 字段 |
| web | 设备表单加「采样周期(ms)」输入 |

### 需求二：历史数据保留时长可配置

| 层 | 改动 |
|---|---|
| store | Config 加 `retentionSeconds`（默认 30 天=2592000，0=永久）+ `retentionCheckMs`（默认 5 分钟）；`cleanup()` 按「全局 + 设备覆盖」删过期 `poll_data`；启动 + 定时清理；`setRetentionSeconds/getRetentionSeconds` 运行时改全局并立即清理 |
| config | `monitor_objects.data_retain_seconds`（NULL=跟随全局，0=永久） |
| mcp | 新增 `set_data_retention(retention_seconds, device_id?)` / `get_data_retention(device_id?)`（设备覆盖优先于全局） |
| api | `POST /api/monitor_objects` 透传 `slaveId/pollIntervalMs/dataRetainSeconds`；新增 `GET/POST /api/retention` |
| web | 设置页「数据管理」加历史保留下拉（1h/6h/24h/7d/30d/90d/永久/自定义） |

- 验证：`npx tsx scripts/test-poll-interval.ts`（设备 100ms → 600ms 内约 6 次采样，非 1s 一次）、`npx tsx scripts/test-retention.ts`（全局 600s 保留 5min 数据、设备覆盖 60s 删 5min 数据、0=永久）、`npm run build:web` 通过；既有回归全通过。

### 诚实标注（PRD §3.5）

- 1ms 只是允许设置的下限，实际采样率 = `max(1ms, Modbus 通信往返时间)`（TCP 局域网 1~5ms、RTU 9600 约 40~50ms）。

## 十五、串口重连不再等冷却期

### 症状

- RTU 串口设备有时首次连接失败（CH340/CP2102 open 较慢），进连接冷却后需手动「断开→连接」才恢复，表现为「要点一下连接才刷新」。

### 修复

- `markDisconnected()` / `reconnectDevice()` 断开时清除 `connectCooldown`，用户手动重连立即重试，不再残留旧冷却。
- `connectTimeoutMs` 默认 3000 → 5000（CH340/CP2102 首次 open 可能较慢，放宽超时）。

- 验证：`npx tsx scripts/test-reconnect-cooldown.ts`（连接失败 → 断开 → 重连，connect 次数 1→2，即立即重试）、既有 12 项回归全通过。

## 十六、串口断开后自动恢复轮询

### 症状

- RTU 串口 timeout/拔出后，物理上恢复了，但 web 数据不更新——因为 `SerialDriver.ready` 一直是 true，poller 一直复用旧串口句柄，读不进来。

### 修复

- `SerialDriver` 监听串口运行期 `close`/`error` 事件（仅当仍是当前端口时），置 `ready=false`，让 `getDriver` 下次重建连接重开串口。

- 验证：`npx tsx scripts/test-rtu-unplug.ts`（close → disconnected → 重连恢复）、既有 15 项回归全通过。

---

## 十七、串口慢设备不堆爆轮询队列

### 症状

- 串口设备读得慢（如 bootloader 每帧几百 ms）时，全局 tick 每轮都往串口队列塞一个轮询，队列越积越长，数据越来越旧，软件像「卡住」但串口又一直在收发。

### 修复

- poller 加 `rtuBusy` 标记：同一条串口上一轮还没读完就跳过本轮，保证最多 1 个在途轮询（写操作仍正常排队串行）。

- 验证：`npx tsx scripts/test-rtu-queue.ts`（读 250ms、tick 50ms，1s 内 4 次读，stopAll 后无排队继续读）、既有 17 项回归全通过。
